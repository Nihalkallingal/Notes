How to use this guide

This guide teaches Angular in two passes. Part I walks the classic Angular you'll meet in most existing codebases — NgModules, decorator inputs, structural directives, RxJS-driven state, Zone.js. Part II then teaches the modern way each of those evolved into — standalone components, signals, built-in control flow, zoneless change detection — and why the change happened.

Learning the old first is deliberate: it's what you'll read on day one of a real job, it makes the modern improvements obvious (you feel the boilerplate the new APIs remove), and interviewers test both. Don't write new code the classic way — but you must recognise and refactor it.

01

What Angular is & why it exists

Beginner

Angular is a full, opinionated framework (not just a library) by Google for building single-page and server-rendered web apps in TypeScript. Unlike React, which gives you a view layer and lets you assemble the rest, Angular ships routing, forms, HTTP, testing, and a CLI in one batteries-included package with strong conventions.

The mental model

  • Components — reusable UI building blocks (a class + template + styles).
  • Templates — HTML extended with Angular syntax for binding and control flow.
  • Services + DI — shared logic injected where needed instead of imported manually.
  • Signals / RxJS — two reactivity systems for state that changes over time.
Why a framework, not a library?Large teams benefit from consistency: every Angular project looks structurally similar, so engineers move between codebases quickly. The trade-off is more upfront concepts and a steeper start than React/Vue.
AngularJS ≠ Angular"AngularJS" means version 1.x (2010–2016): JavaScript, $scope, controllers, the digest cycle. "Angular" means 2+ — a complete TypeScript rewrite. This guide is about Angular (2+). Even Part I's "classic" content is modern-era Angular, just the pre-signals style.

Part I · learn this first

Classic Angular

The conventions that built almost every Angular app you'll inherit: NgModules, decorator-based inputs, structural directives, constructor injection, RxJS for state, and Zone.js change detection. Solid, battle-tested — and still everywhere.

02

Classic setup & NgModules

Beginner

You need Node.js (LTS) and the Angular CLI. Classic projects were generated with NgModules enabled and bootstrapped a root AppModule.

terminal
# Install the CLI
npm install -g @angular/cli

# Older CLI flag to scaffold a module-based app
ng new my-app --standalone=false
ng serve                          # dev server at http://localhost:4200

ng g component user-card          # adds the component to a module's declarations
ng g module shared                # a SharedModule for common UI

NgModules — the old organising unit

Before standalone components, every component, directive, and pipe had to be declared in an @NgModule. Shared code lived in modules you imported. The root AppModule bootstrapped the app.

app.module.ts
import { NgModule } from '@angular/core';
import { BrowserModule } from '@angular/platform-browser';
import { FormsModule } from '@angular/forms';

@NgModule({
  declarations: [AppComponent, UserCard],   // every component listed here
  imports: [BrowserModule, FormsModule],     // pull in other modules
  providers: [AuthService],                  // services for this module
  bootstrap: [AppComponent],                 // root component
})
export class AppModule {}
main.ts (classic bootstrap)
import { platformBrowserDynamic } from '@angular/platform-browser-dynamic';
import { AppModule } from './app/app.module';

platformBrowserDynamic().bootstrapModule(AppModule);
Why NgModules existedThey gave Angular a unit of compilation and a place to wire up declarations, dependency providers, and lazy-load boundaries. The cost: indirection — you'd hunt across modules to find where something was declared, and SharedModules became dumping grounds. Part II shows the standalone replacement.
03

Components & decorator inputs/outputs

Beginner

A component is a class decorated with @Component. Classically it was declared in a module (not standalone), received data through @Input() properties, and emitted events through @Output() + EventEmitter.

user-card.component.ts (classic)
import { Component, Input, Output, EventEmitter } from '@angular/core';

@Component({
  selector: 'app-user-card',
  template: `
    <article class="card">
      <h3>{{ name }}</h3>
      <button (click)="select.emit(name)">Choose</button>
    </article>
  `,
})
export class UserCard {
  @Input() name = '';                  // data in, read as a plain property
  @Output() select = new EventEmitter<string>();  // events out
}

Lifecycle hooks

Hooks run code at points in a component's life. Classically you leaned on them heavily:

  • ngOnInit() — once after inputs are set; initial data fetch.
  • ngOnChanges() — every time an @Input changes; react to new values.
  • ngOnDestroy() — cleanup: unsubscribe, clear timers.
Why so many hooks classically?Without signals, the framework couldn't tell you precisely what changed, so you hooked into lifecycle moments and manually reconciled. Part II's signal inputs make much of ngOnChanges unnecessary.

Templates: binding & structural directives

Beginner

Binding connects class data to the template. The four kinds are unchanged across eras:

SyntaxDirectionExample
Interpolationclass → view{{ title }}
Propertyclass → view[disabled]="isLoading"
Eventview → class(click)="save()"
Two-wayboth[(ngModel)]="email"

Structural directives — the classic control flow

Conditionals and loops used the *-prefixed directives *ngIf, *ngFor, and *ngSwitch, which required importing CommonModule. Lists used a trackBy function to keep DOM identity stable.

classic template
<p *ngIf="user; else signIn">Welcome, {{ user.name }}</p>
<ng-template #signIn><p>Please sign in.</p></ng-template>

<li *ngFor="let item of items; trackBy: trackById">
  {{ item.label }}
</li>

<div [ngSwitch]="status">
  <spinner *ngSwitchCase="'loading'"></spinner>
  <p *ngSwitchDefault>Ready</p>
</div>
component (trackBy fn)
trackById(index: number, item: Item) {
  return item.id;       // tells Angular how to identify list rows
}
Why trackBy matteredWithout it, *ngFor could destroy and recreate every row on each change, killing performance on big lists. It was optional — and forgetting it was a classic bug. Part II makes track mandatory.
05

Services & constructor DI

Intermediate

A service holds shared logic or state (e.g. an API client). Dependency injection means Angular constructs and supplies these for you. Classically you declared dependencies as constructor parameters, and registered services either in providedIn:'root' or a module's providers array.

auth.service.ts (classic)
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { BehaviorSubject } from 'rxjs';

@Injectable({ providedIn: 'root' })
export class AuthService {
  private user$ = new BehaviorSubject<User | null>(null);
  readonly user = this.user$.asObservable();

  // Classic: dependencies arrive as constructor parameters
  constructor(private http: HttpClient) {}

  login(email: string) {
    return this.http.post<User>('/api/login', { email });
  }
}
Why DI at all?It inverts control: a component asks for what it needs and Angular decides how to build it. In tests you provide a mock; in production the real thing — consumer code never changes. A perennial interview topic.
Provider scopesprovidedIn:'root' = app-wide singleton. Listing a service in a component's providers = a new instance per component. Module providers scoped it to that module.
06

RxJS-driven state & the async pipe

Advanced

Before signals, RxJS was the only reactivity system. Component state was commonly held in a BehaviorSubject and rendered through the async pipe, which subscribes and unsubscribes for you.

Core concepts

TermMeaning
ObservableA lazy stream you subscribe to.
SubjectAn observable you can also push values into; multicasts.
BehaviorSubjectA Subject holding & replaying its latest value (needs an initial value).
ReplaySubjectReplays a configurable buffer of recent values to new subscribers.
OperatorA pure function transforming one observable into another.
classic state with async pipe
// component
count$ = new BehaviorSubject(0);
doubled$ = this.count$.pipe(map(n => n * 2));
inc() { this.count$.next(this.count$.value + 1); }

// template — async pipe handles subscribe/unsubscribe
<p>{{ count$ | async }} → {{ doubled$ | async }}</p>

The flattening operators (most-asked in interviews)

OperatorBehaviourUse
switchMapCancels the previous inner observable on a new value.Type-ahead search.
mergeMapRuns inner observables concurrently.Parallel requests.
concatMapQueues them in order, one at a time.Ordered saves.
exhaustMapIgnores new values while one is in flight.Prevent double submits.
type-ahead search
import { debounceTime, distinctUntilChanged, switchMap, catchError } from 'rxjs/operators';
import { of } from 'rxjs';

results$ = this.searchControl.valueChanges.pipe(
  debounceTime(300),              // wait for a pause in typing
  distinctUntilChanged(),         // ignore unchanged values
  switchMap(q => this.api.search(q).pipe(
    catchError(() => of([])),     // keep the stream alive on error
  )),
);

Operators worth memorising

  • Transform: map, scan, tap (side-effects).
  • Filter: filter, take, takeUntil, first, skip.
  • Combine: combineLatest, forkJoin (wait for all), withLatestFrom, merge, zip.
  • Utility: debounceTime, throttleTime, retry, startWith, shareReplay.
Classic leak pitfallManual .subscribe() in a component leaks unless you unsubscribe in ngOnDestroy (often via a takeUntil(destroy$) pattern). Preferring the async pipe avoided most leaks. Part II adds takeUntilDestroyed() and signal conversion.
07

Routing: module lazy loading & class guards

Intermediate

The router maps URLs to components. Classically, lazy loading pulled in feature modules via loadChildren, route protection used class-based guards implementing the CanActivate interface, and params were read by subscribing to ActivatedRoute.

app-routing.module.ts (classic)
const routes: Routes = [
  { path: '', component: HomeComponent },
  { path: 'users/:id', component: UserComponent },
  {
    path: 'admin',
    canActivate: [AuthGuard],                  // a class guard
    loadChildren: () => import('./admin/admin.module')
      .then(m => m.AdminModule),               // lazy-loads a MODULE
  },
  { path: '**', component: NotFoundComponent },
];
auth.guard.ts (class guard) + reading params
@Injectable({ providedIn: 'root' })
export class AuthGuard implements CanActivate {
  constructor(private auth: AuthService, private router: Router) {}
  canActivate() {
    return this.auth.isLoggedIn() ? true : this.router.parseUrl('/login');
  }
}

// reading a route param, classic style
constructor(private route: ActivatedRoute) {}
ngOnInit() {
  this.route.paramMap.subscribe(p => this.id = p.get('id'));
}

Forms: template-driven & reactive

Intermediate

Two classic approaches, both still fully supported:

  • Template-driven — simple forms via [(ngModel)] and FormsModule; logic lives in the template.
  • Reactive forms — the form model is defined in the class with FormGroup/FormControl and ReactiveFormsModule. Explicit, testable, scales well — the classic default for non-trivial forms.
reactive-form.component.ts
import { Component } from '@angular/core';
import { FormBuilder, Validators } from '@angular/forms';

@Component({
  template: `
    <form [formGroup]="form" (ngSubmit)="submit()">
      <input formControlName="email" placeholder="Email" />
      <small *ngIf="form.get('email')?.invalid && form.get('email')?.touched">
        Valid email required
      </small>
      <button [disabled]="form.invalid">Sign up</button>
    </form>
  `,
})
export class SignupForm {
  constructor(private fb: FormBuilder) {}
  form = this.fb.group({
    email: ['', [Validators.required, Validators.email]],
  });
  submit() { if (this.form.valid) console.log(this.form.value); }
}
valueChangesClassic reactive forms expose changes as Observables (form.valueChanges, control.statusChanges) you subscribe to — powerful, but more wiring than signal forms (Part II).
09

HttpClient & class interceptors

Intermediate

HttpClient makes API calls returning Observables. Classically you imported HttpClientModule in a module, subscribed to responses (or used the async pipe), and added cross-cutting behaviour through class interceptors registered with the HTTP_INTERCEPTORS multi-token.

auth.interceptor.ts (class) + registration
@Injectable()
export class AuthInterceptor implements HttpInterceptor {
  intercept(req: HttpRequest<any>, next: HttpHandler) {
    const token = localStorage.getItem('token');
    const authReq = token
      ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
      : req;
    return next.handle(authReq);
  }
}

// registered in a module's providers
providers: [
  { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true },
]
Why interceptors?Auth tokens, logging, global error handling, retries — these shouldn't be copy-pasted into every request. Interceptors centralise them so every HTTP call passes through one pipeline. The pattern survives in Part II; only the syntax slims down.
10

Zone.js change detection

Advanced

Change detection (CD) is how Angular decides when to update the DOM. Classic Angular relied on Zone.js, which monkey-patches every async API (timers, events, XHR) so the framework knows "something might have changed" and re-checks components.

The two classic strategies

  • Default — re-check the whole component tree on every event. Simple, wasteful.
  • OnPush — re-check a component only when its inputs change (by reference), an event fires in it, or you call markForCheck(). The classic performance lever.
opting into OnPush (classic)
@Component({
  selector: 'app-list',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `...`,
})
export class ListComponent {
  constructor(private cdr: ChangeDetectorRef) {}
  refresh() { this.cdr.markForCheck(); }  // nudge CD manually
}
The classic painOnPush relied on reference changes — mutating an array in place wouldn't trigger an update, a notorious bug source. And Zone.js added ~100KB and forced broad tree checks. Part II's signals solve both: precise notifications and no Zone.js at all.

Part II · the way you build today

Modern Angular

The signal-first era. Each section here is the direct successor to a Part I topic — standalone replaces modules, signals replace BehaviorSubjects, built-in control flow replaces structural directives, zoneless replaces Zone.js. We lead each with what changed and why.

Standalone components & inject()

Beginner

Replaces: NgModules (§02) and constructor DI (§05).

Standalone components declare their own dependencies via an imports array — no NgModule needed. App-wide providers move to a small app.config.ts. Standalone is the default since v19.

Classic — NgModule
app.module.ts
@NgModule({
  declarations: [App, UserCard],
  imports: [BrowserModule, FormsModule],
  bootstrap: [App],
})
export class AppModule {}
Modern — standalone
app.ts + app.config.ts
@Component({
  selector: 'app-root',
  imports: [UserCard, FormsModule],
  template: `...`,
})
export class App {}

// app.config.ts
export const appConfig = {
  providers: [provideHttpClient(), provideRouter(routes)],
};

inject() over constructor params

Classic
constructor DI
constructor(
  private http: HttpClient,
  private auth: AuthService,
) {}
Modern
inject()
private http = inject(HttpClient);
private auth = inject(AuthService);
Why the changeStandalone removes the indirection of hunting across modules and makes lazy loading trivial. inject() works outside constructors (functions, guards, field initialisers) and reads cleaner with many dependencies. Both DI styles still work — migration is incremental.

Built-in control flow & signal inputs

Beginner

Replaces: structural directives (§04) and decorator inputs/outputs (§03).

Since v17, control flow is built into the compiler — no CommonModule import, faster, and @for makes track mandatory.

Classic
*ngIf / *ngFor
<p *ngIf="user">{{ user.name }}</p>

<li *ngFor="let i of items;
        trackBy: trackById">
  {{ i.label }}
</li>
Modern
@if / @for
@if (user(); as u) { <p>{{ u.name }}</p> }

@for (i of items(); track i.id) {
  <li>{{ i.label }}</li>
} @empty { <li>None yet.</li> }

Signal inputs & outputs

Classic
decorator I/O
@Input() name = '';
@Output() select = new EventEmitter<string>();
select.emit(this.name);
Modern
input() / output()
name = input.required<string>();
select = output<string>();
select.emit(this.name());  // name is a signal
Why the changeThe block syntax needs no imports and is compiler-optimised; mandatory track prevents a whole class of list-rerender bugs that trackBy left optional. Signal inputs make inputs reactive — they slot directly into computed() with no ngOnChanges.

Signals — the new reactive core

Intermediate

Replaces: RxJS-for-state and BehaviorSubjects (§06) for synchronous UI state.

A signal wraps a value and notifies its dependents when it changes. It's Angular's primary reactivity primitive since v16 and the foundation of everything modern.

Classic state
BehaviorSubject
count$ = new BehaviorSubject(0);
doubled$ = this.count$.pipe(map(n => n*2));
inc() { this.count$.next(this.count$.value+1); }
// template: {{ count$ | async }}
Signals
signal / computed
count = signal(0);
doubled = computed(() => this.count() * 2);
inc() { this.count.update(n => n + 1); }
// template: {{ count() }}
PrimitiveUse it for
signal()Mutable state you set directly (.set(), .update()).
computed()Derived, cached values that recompute when deps change.
effect()Side-effects (logging, DOM, storage) — not for deriving state.
linkedSignal()Writable state that resets when a source changes (v19+).
resource()Async data as a signal (stable v22) — see §17.
Why signals beat plain variables and BehaviorSubjects for UI stateA plain property change can't tell the framework what changed; a BehaviorSubject can, but needs subscriptions, the async pipe, and operator plumbing for simple cases. Signals build a precise dependency graph synchronously — when count changes, only the views/computeds reading it update. This is exactly what makes zoneless possible.
Signals vs RxJS — the interview lineUse signals for synchronous UI state, RxJS for streams over time (HTTP, websockets, debounced input). They're not competitors. Bridge with toSignal() / toObservable().
14

Change detection & going zoneless

Advanced

Replaces: Zone.js change detection (§10).

With signals giving exact change information, Zone.js is no longer needed. New projects are zoneless by default since v21, and OnPush is the default strategy as of v22.

app.config.ts — zoneless
import { provideZonelessChangeDetection } from '@angular/core';

export const appConfig = {
  providers: [ provideZonelessChangeDetection() ],  // drop Zone.js
};
  • OnPush now also re-checks when a signal a component reads changes — so signals + OnPush gives precise updates with no manual markForCheck().
  • Zoneless removes Zone.js entirely; signals drive every update.
Why kill Zone.jsIt patched everything, added ~100KB, forced broad tree checks, and muddied stack traces. Signals provide exact change info instead. Zoneless apps render faster with far fewer needless re-renders.
Migration realityExisting apps keep Zone.js until you opt out. Going zoneless means anything that previously relied on Zone to trigger CD (mutating a plain array in place) must now use signals or immutable updates.

Functional guards & loadComponent

Intermediate

Replaces: module lazy loading & class guards (§07).

app.routes.ts (modern)
export const routes: Routes = [
  { path: '', component: HomePage },
  { path: 'users/:id', component: UserPage },
  {
    path: 'admin',
    canActivate: [authGuard],                       // functional guard
    loadComponent: () => import('./admin/admin.page')
      .then(m => m.AdminPage),                    // lazy COMPONENT, not module
  },
  { path: '**', component: NotFoundPage },
];
auth.guard.ts (functional)
export const authGuard: CanActivateFn = () => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.user() ? true : router.createUrlTree(['/login']);
};
Params as inputsWith withComponentInputBinding(), a :id route fills an id = input() automatically — no ActivatedRoute subscription needed.
16

Signal Forms

Intermediate

Joins: template-driven & reactive forms (§08), which remain supported.

Signal Forms model a form as a tree of signals, so value, validity, and errors are all signals you read directly — no valueChanges subscriptions. Introduced experimentally in v21, stable in Angular 22.

What changed & whyReactive forms expose state as Observables, which means subscriptions and async-pipe plumbing for what is fundamentally synchronous form state. Signal Forms remove that boilerplate and integrate with the rest of the signal world. Migrate incrementally — reactive forms aren't going away.
Practical adviceFor a new signal-based app, reach for Signal Forms. In an existing reactive-forms codebase, keep what works and adopt Signal Forms for new screens. Know both for interviews.

Functional interceptors & resource()

Intermediate

Replaces: class interceptors & manual subscription (§09).

Classic interceptor
class + token
@Injectable()
class AuthInterceptor implements HttpInterceptor {
  intercept(req, next) { ... return next.handle(r); }
}
{ provide: HTTP_INTERCEPTORS,
  useClass: AuthInterceptor, multi: true }
Functional interceptor
HttpInterceptorFn
export const authInterceptor: HttpInterceptorFn =
  (req, next) => {
    const t = localStorage.getItem('token');
    return next(t
      ? req.clone({ setHeaders:{ Authorization:`Bearer ${t}` }})
      : req);
  };
// provideHttpClient(withInterceptors([authInterceptor]))

The Resource API (stable in v22)

Instead of manually subscribing, resource() turns async data into signals with built-in loading/error/value state.

user.page.ts
userId = signal(1);
userResource = resource({
  params: () => ({ id: this.userId() }),       // re-fetches when id changes
  loader: async ({ params }) =>
    (await fetch(`/api/users/${params.id}`)).json(),
});
// template: userResource.value(), .isLoading(), .error()

RxJS today & bridging to signals

Advanced

Builds on: classic RxJS (§06) — the operators are identical; the role narrows.

RxJS isn't going away — it's still the right tool for event streams over time. What changed: you no longer use it for simple UI state (signals do that), and teardown got easier.

modern leak-free RxJS
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

this.api.events$
  .pipe(takeUntilDestroyed())     // auto-unsubscribes on destroy
  .subscribe(e => this.handle(e));
bridging RxJS ↔ signals
import { toSignal, toObservable } from '@angular/core/rxjs-interop';

results = toSignal(this.api.search$, { initialValue: [] });  // stream → signal
query$  = toObservable(this.query);                          // signal → stream
When to still use RxJSType-ahead search (debounceTime + switchMap), websockets, polling, combining multiple async sources, complex cancellation. For a value that just changes, use a signal.
19

State management

Advanced

Options, smallest to largest:

  • Signal-based service — a service exposing signals + computed. Enough for most apps now.
  • NgRx SignalStore — lightweight, signal-first store; the modern community default.
  • NgRx Store (Redux-style) — actions, reducers, effects, selectors. Heavy but predictable; common in large enterprises and classic codebases.
cart.store.ts — signal service
@Injectable({ providedIn: 'root' })
export class CartStore {
  private _items = signal<Item[]>([]);
  readonly items = this._items.asReadonly();
  readonly total = computed(() =>
    this._items().reduce((s, i) => s + i.price, 0));

  add(item: Item)    { this._items.update(xs => [...xs, item]); }
  remove(id: string) { this._items.update(xs => xs.filter(i => i.id !== id)); }
}
Why not always NgRx?Redux-style stores add boilerplate that only pays off at scale (many features sharing state, time-travel debugging, strict audit trails). A signal service handles most cases with far less code — picking the lighter tool shows judgment.

Performance, SSR & hydration

Advanced
  • OnPush + signals — minimise CD work (now the default).
  • @defer — lazy-load heavy template blocks on a trigger.
  • track in @for — stable list identity, no full re-renders.
  • SSR + hydration — server-render HTML for fast first paint and SEO, then hydrate on the client.
deferred loading
@defer (on viewport) {                  // load when scrolled into view
  <heavy-chart [data]="data()" />
} @placeholder { <p>Scroll to load…</p> }
  @loading (minimum 200ms) { <spinner /> }
// triggers: on idle | hover | interaction | timer(2s) | when cond()
Incremental hydrationModern Angular SSR hydrates only the parts of the page that are needed or interacted with, instead of the whole tree — shipping and running less JavaScript on first load. Early adopters report markedly faster initial renders.

Testing

Advanced

Angular ships TestBed for unit and component tests. As of v21, Vitest is the default runner (replacing Karma); E2E is typically Playwright or Cypress.

user-card.spec.ts
import { TestBed } from '@angular/core/testing';
import { UserCard } from './user-card.component';

describe('UserCard', () => {
  it('renders the name input', () => {
    const fixture = TestBed.createComponent(UserCard);
    fixture.componentRef.setInput('name', 'Ada');
    fixture.detectChanges();
    expect(fixture.nativeElement.textContent).toContain('Ada');
  });
});
What to testUnit-test services and pure logic; component-test rendering and interaction; mock HTTP with provideHttpClientTesting(). Interviewers ask what you'd test — prioritise behaviour over implementation details.

What changed recently — & why (v17 → v22)

Advanced

Angular ships on a 6-month major cadence. Knowing the trajectory — and the reasoning — signals that you keep current.

VersionHeadline changesWhy
v17 (2023)Built-in control flow (@if/@for/@switch), @defer, rebrand.Compiler-level control flow; no CommonModule; ergonomic lazy rendering.
v18 (2024)Zoneless CD (experimental), Material 3, event replay.Begin removing the Zone.js dependency.
v19 (2024)Standalone by default, linkedSignal(), incremental hydration, resource() preview.Drop NgModule boilerplate; richer signals; less first-load JS.
v20 (2025)Signal APIs matured, granular hydration, template polish.~30–40% faster initial renders; ~50% fewer needless re-renders.
v21 (Nov 2025)Zoneless default for new projects; Vitest replaces Karma; Signal Forms (experimental); AI/MCP tooling; removes long-deprecated APIs.Commit to signal-first, zoneless architecture; modern tooling.
v22 (Jun 3, 2026)Signal Forms & Resource API stable; OnPush is the new default; selectorless components; stable MCP server; ergonomic APIs.Production-ready maturity of the signal vision; less boilerplate; AI-assisted workflows.
The throughlineEvery recent release pushes one strategy: precise, signal-driven reactivity that removes Zone.js, cuts boilerplate, and ships less JavaScript. "Where is Angular heading?" → signal-first, zoneless, increasingly AI-tooled.

Fundamentals

Is Angular a framework or a library, and why does it matter?

A framework — it calls your code within its structure (inversion of control) and ships routing, DI, forms, HTTP, and a CLI. React is closer to a view library you assemble around. The trade-off is more conventions but more consistency across teams.

Explain the four types of data binding.

Interpolation {{ }} and property [prop] flow class→view. Event (event) flows view→class. Two-way [(ngModel)] combines both (banana-in-a-box = property binding + event binding).

AngularJS vs Angular?

AngularJS is 1.x (2010–2016): JavaScript, $scope, controllers, digest cycle. Angular (2+) is a complete TypeScript rewrite with components and a new DI/reactivity model. Same name and lineage, no shared code.

Classic concepts (Part I)

What were NgModules and what did the root AppModule do?

NgModules grouped declarations (components, directives, pipes), imported other modules, and registered providers. AppModule bootstrapped the app via bootstrapModule. They gave a compilation unit and lazy-load boundary but added indirection — superseded by standalone components.

Why did *ngFor need trackBy, and what went wrong without it?

trackBy told Angular how to identify each row. Without it, a new array reference could make Angular destroy and recreate every DOM node, hurting performance and losing element state (focus, scroll). It was optional and easy to forget — which is why modern @for makes track required.

How did classic OnPush change detection decide to run?

OnPush re-checks a component only when an @Input changes by reference, an event originates inside it, an observable bound via async emits, or you call markForCheck(). The reference-equality requirement meant in-place mutations were missed — a classic bug.

Subject vs BehaviorSubject vs ReplaySubject?

Subject multicasts but new subscribers miss past values. BehaviorSubject holds one current value and replays it (needs an initial value). ReplaySubject replays a configurable buffer of recent values.

How did you avoid subscription leaks in classic Angular?

Prefer the async pipe (auto-unsubscribes), or for manual subscriptions store them and unsubscribe in ngOnDestroy — commonly via a destroy$ Subject piped through takeUntil(destroy$). Modern code uses takeUntilDestroyed().

RxJS operators

switchMap vs mergeMap vs concatMap vs exhaustMap — a real use for each.

switchMap: type-ahead search (cancel stale request). mergeMap: independent parallel calls. concatMap: sequential ordered saves. exhaustMap: ignore repeat clicks while one request is in flight.

combineLatest vs forkJoin?

combineLatest emits whenever any source emits, giving the latest of each (good for live form combinations). forkJoin waits for all sources to complete and emits once (good for firing several requests and acting when all finish).

Modern concepts (Part II)

What is a signal, and how does it differ from an Observable?

A signal is a synchronous container holding a current value that notifies dependents on change — you always read a value with x(). An Observable is an async stream you subscribe to. Signals suit UI state; Observables suit event streams. Bridge with toSignal()/toObservable().

computed() vs effect() — and a common misuse?

computed() derives a cached, pure value from other signals. effect() runs side-effects when deps change. A common misuse is using an effect to set another signal to derive state — that should be a computed(); the effect causes extra runs and harder-to-trace updates.

What is zoneless change detection and why is it significant?

It removes Zone.js, which previously patched async APIs to trigger broad CD sweeps. Signals tell Angular precisely what changed instead. Result: smaller bundle, faster and fewer re-renders, cleaner stack traces. Default for new projects since v21.

Why standalone components over NgModules?

Standalone components declare their own dependencies via imports, removing module indirection, simplifying lazy loading (loadComponent), and cutting boilerplate. Default since v19; NgModules still work for incremental migration.

How do functional guards/interceptors differ from class-based ones?

Classic guards implemented CanActivate on an @Injectable class; interceptors implemented HttpInterceptor.intercept() and were registered via the HTTP_INTERCEPTORS multi-token. Modern equivalents are plain functions (CanActivateFn, HttpInterceptorFn) using inject() — less boilerplate, easier to compose and test.

When would you pick a signal service over NgRx?

For most apps a signal service (signals + computed) is enough and far less code. Reach for NgRx (Store or SignalStore) when many features share complex state, you need auditable transitions, effects coordination, or time-travel debugging. Picking the lighter tool when it fits shows judgment.

Migration (the senior-signal questions)

You inherited a Zone.js app using BehaviorSubjects for state. How do you modernise it?

Incrementally. Migrate UI state from BehaviorSubject + async to signal()/computed(); keep RxJS for genuine streams and bridge with toSignal(). Convert components to standalone, move guards/interceptors to functional form, adopt OnPush, then go zoneless once signals drive the UI. Old and new coexist — no big-bang rewrite.

What's the most recent stable version and one headline feature?

Angular 22, released June 3, 2026. Headline: Signal Forms and the Resource API became stable, and OnPush became the default change-detection strategy — cementing the signal-first, zoneless direction.
