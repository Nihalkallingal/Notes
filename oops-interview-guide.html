Fundamentals

The foundation of every OOP interview. Get these definitions crisp — interviewers use them as a filter in the first two minutes.
FresherWhat is the difference between a class and an object?

A class is a compile-time blueprint — a named type that defines the structure (fields) and behaviour (methods) of the entities it will represent. An object is a runtime entity: a specific instance of a class allocated in memory, with its own copy of instance state.

Why it matters: Every OOP construct (inheritance, polymorphism, encapsulation) depends on this distinction. Confusing static members with instance members is a direct consequence of blurring class vs object.

Java 
// CLASS — a compile-time blueprint
class Car {
    String model;   // instance field (state)
    int speed;      // instance field (state)

    void accelerate(int by) { speed += by; } // behaviour
}

// OBJECT — a runtime instance
Car tesla  = new Car();  // 'tesla' holds a reference to an object on the heap
Car toyota = new Car();  // separate object; different state

tesla.model = "Model S";
toyota.model = "Corolla";
// tesla and toyota share the same CLASS but have independent state
Interviewers listen for: Use the word "blueprint" or "template" for class, and "runtime entity" or "instance" for object. Mention that a class is a compile-time concept while an object exists at runtime on the heap.
Common mistake: Saying "a class is a group of objects." It is the opposite — a class defines what objects look like. Objects are instances of a class, not constituents of it.
FresherWhat is state vs behaviour in OOP?

State is the data an object holds at any given moment — its instance variables. Behaviour is what an object can do — its methods that may read or mutate that state.

Separating what an object knows from what it does is the conceptual backbone of OOP design.

Java 
class BankAccount {
    // --- STATE ---
    private String owner;
    private double balance;

    BankAccount(String owner, double initial) {
        this.owner   = owner;
        this.balance = initial;
    }

    // --- BEHAVIOUR ---
    void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance += amount;
    }

    boolean withdraw(double amount) {
        if (amount > balance) return false;
        balance -= amount;
        return true;
    }

    double getBalance() { return balance; }
}
FresherWhat is instantiation? Walk me through what `new` does in Java.

Instantiation is the process of creating an object from its class. In Java, new performs four steps:

  1. Allocates memory on the heap for the new object's fields.
  2. Initialises fields to default values (0, null, false).
  3. Executes any instance initialiser blocks in textual order.
  4. Calls the constructor body.

The result is a reference (a managed pointer) to the newly created object.

Java 
BankAccount acc = new BankAccount("Alice", 500.0);
//                ^^^  heap allocation + constructor call
// acc is a reference; the object lives on the heap
// if acc is reassigned or goes out of scope, the GC may reclaim the object

BankAccount ref2 = acc; // ref2 points to the SAME object, not a copy
ref2.deposit(100.0);
System.out.println(acc.getBalance()); // 600.0 — same object mutated
Common mistake: Saying Java passes objects by reference. Java is strictly pass-by-value — the value passed is the reference (address). You cannot make the caller's variable point to a different object inside a method.

FresherWhat is message passing, and why does OOP exist?

Message passing means objects communicate by invoking methods on each other. The sending object does not need to know the receiving object's implementation — only its public interface. This is the mechanism behind polymorphism and loose coupling.

OOP exists to manage the complexity of large systems by:

  • Modularity: Objects are self-contained; changes in one rarely break others.
  • Reusability: Classes can be extended and composed.
  • Maintainability: Encapsulation hides implementation details behind stable interfaces.
  • Modelling: Code maps naturally to real-world entities and relationships.
Java 
class Logger {
    void log(String msg) { System.out.println("[LOG] " + msg); }
}

class OrderService {
    private Logger logger; // HAS-A relationship

    OrderService(Logger logger) { this.logger = logger; }

    void placeOrder(String item) {
        // Message passing: sending the "log" message to the Logger object
        // OrderService doesn't care HOW Logger logs — only that it can
        logger.log("Order placed: " + item);
    }
}
// Swap Logger for a FileLogger, DatabaseLogger, etc. — OrderService is unchanged

The Four Pillars of OOP

Every OOP interview includes these. The trap is giving a one-line textbook definition. Demonstrate understanding with concrete consequences — what breaks when you violate each pillar.
FresherExplain encapsulation with an example.

Definition: Encapsulation bundles data (fields) and the methods that operate on that data together in a single unit (class), and controls access to the internals using access modifiers. External code must go through a defined interface.

Why it matters: Prevents external code from placing an object in an invalid state. Changes to internal representation do not break callers.

Java 
public class Circle {
    private double radius; // HIDDEN — external code cannot set this directly

    public Circle(double radius) {
        setRadius(radius); // reuse validation
    }

    public double getRadius() { return radius; }

    public void setRadius(double radius) {
        if (radius <= 0) throw new IllegalArgumentException("Radius must be > 0");
        this.radius = radius; // validated write
    }

    public double area() { return Math.PI * radius * radius; }
}

// Usage
Circle c = new Circle(5);
// c.radius = -3;  // compile error — field is private
c.setRadius(-3);   // throws IllegalArgumentException — invariant enforced
Interviewers listen for: "Controlled access to internal state" and "invariant enforcement." A bare getter/setter pair with no validation is technically encapsulation in structure but misses the purpose. Say so.
FresherExplain abstraction with an example.

Definition: Abstraction means exposing only the relevant interface of an object and hiding the complexity of its implementation. The user interacts with a simplified model, not the underlying machinery.

Why it matters: Reduces cognitive load. Allows implementations to evolve independently of callers.

Java 
// Abstract interface — the public contract callers depend on
interface PaymentGateway {
    boolean processPayment(double amount, String currency);
    boolean refund(String transactionId);
}

// Concrete implementation — hidden complexity
class StripeGateway implements PaymentGateway {
    @Override
    public boolean processPayment(double amount, String currency) {
        // Stripe REST calls, HMAC signing, retry logic, idempotency keys...
        return true; // caller sees only success/failure
    }
    @Override
    public boolean refund(String transactionId) { return true; }
}

// Caller knows nothing about Stripe internals
void checkout(PaymentGateway gateway, double total) {
    if (!gateway.processPayment(total, "USD")) throw new RuntimeException("Payment failed");
}
// Swap StripeGateway for PayPalGateway with zero changes to checkout()
FresherExplain inheritance with an example.

Definition: Inheritance allows a subclass (child) to acquire the fields and methods of a superclass (parent), establishing an IS-A relationship. The subclass may specialise (override) inherited behaviour.

Why it matters: Enables code reuse and the open/closed principle — extend without modifying existing code.

Java 
class Animal {
    protected String name;
    Animal(String name) { this.name = name; }
    String speak() { return "..."; }          // default behaviour
    void breathe() { System.out.println(name + " breathes."); } // inherited as-is
}

class Dog extends Animal {
    Dog(String name) { super(name); }         // calls Animal constructor
    @Override String speak() { return "Woof!"; } // specialises behaviour
    void fetch() { System.out.println(name + " fetches!"); } // new behaviour
}

class Cat extends Animal {
    Cat(String name) { super(name); }
    @Override String speak() { return "Meow!"; }
}

// IS-A: a Dog IS AN Animal
Animal a = new Dog("Rex");
System.out.println(a.speak()); // "Woof!" — runtime polymorphism
a.breathe();                   // inherited, not overridden
Common mistake: Overusing inheritance for code reuse when composition is more appropriate. Prefer IS-A for inheritance, HAS-A for composition. "A Dog IS-AN Animal" is a genuine IS-A. "An Engine IS-A Car" is not.
FresherExplain polymorphism with an example.

Definition: Polymorphism (Greek: "many forms") allows a single interface to represent different underlying types. A superclass reference can point to any subclass object, and the correct method is selected at runtime based on the actual type.

Why it matters: Enables the open/closed principle and extensibility — add new types without modifying existing code that uses the interface.

Java 
abstract class Shape {
    abstract double area();
    void describe() { System.out.println("Area = " + area()); }
}

class Circle extends Shape {
    double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

class Rectangle extends Shape {
    double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }
    @Override double area() { return w * h; }
}

// Polymorphic usage — SAME code handles ALL Shape types
Shape[] shapes = { new Circle(3), new Rectangle(4, 5), new Circle(7) };
for (Shape s : shapes) {
    s.describe(); // dispatch to Circle.area() or Rectangle.area() at runtime
}
// Adding Triangle only requires a new class; this loop is UNCHANGED
MidWhat is the difference between abstraction and encapsulation? This trips up most candidates.

This is the single most commonly confused concept in OOP interviews. They are related but distinct:

DimensionAbstractionEncapsulation
WhatHiding complexity / exposing essentialsHiding data / bundling data with methods
FocusDesign level — WHAT the object doesImplementation level — HOW access is restricted
Achieved viaAbstract classes, interfaces, APIsAccess modifiers (private, protected)
GoalReduce cognitive complexity for callersMaintain object invariants; hide internals
MetaphorCar steering wheel — you turn, it steers; you don't see the rack-and-pinionEngine under the bonnet — panels prevent you touching live components

The key insight: abstraction is achieved through encapsulation, but they are not the same thing. Encapsulation is the mechanism; abstraction is the design goal.

Java 
// ABSTRACTION: interface exposes only what callers need
interface Stack<T> {
    void push(T item);
    T pop();
    T peek();
    boolean isEmpty();
}

// ENCAPSULATION: implementation hides internal representation
class ArrayStack<T> implements Stack<T> {
    private Object[] data;   // private — implementation detail
    private int top = -1;    // private — callers cannot corrupt this

    @SuppressWarnings("unchecked")
    public ArrayStack(int capacity) { data = new Object[capacity]; }

    @Override public void push(T item) { data[++top] = item; }
    @Override public T pop()  { return (T) data[top--]; }
    @Override public T peek() { return (T) data[top]; }
    @Override public boolean isEmpty() { return top == -1; }
}
// A caller using Stack<T> is abstracted from BOTH the interface choice
// AND the array-based representation inside ArrayStack
Interviewers listen for: The phrase "abstraction is WHAT, encapsulation is HOW." Also: an interface provides abstraction but not encapsulation (the interface itself has no state to hide); the implementing class provides encapsulation.

MidWhat access modifier rules apply when overriding a method?

When overriding, the overriding method may not restrict visibility but may widen it. This preserves the Liskov Substitution Principle: a caller using the supertype must be able to call the method on any subtype.

Java 
class Parent {
    protected void display() { System.out.println("Parent"); }
}

class Child extends Parent {
    @Override
    public void display() { System.out.println("Child"); } // OK — widened to public

    // @Override
    // private void display() { }  // COMPILE ERROR — narrowed visibility
}

Access modifier widening order (narrowest to broadest): private → default → protected → public. Overrides can only move rightward in this order.

MidWhy not make everything public? What is the principle at play?

Making everything public violates the Principle of Least Privilege and breaks encapsulation. The consequences:

  • Coupling: External code can reach into internals, making refactoring impossible without breaking callers.
  • Invariant violation: Any code anywhere can set a field to an invalid value.
  • API surface: Everything public becomes part of your API contract, which you must maintain forever.

The guideline: start with private and widen only when required. Make fields private and expose controlled getters/setters or behaviour-rich methods.

Common mistake: Thinking Java's private hides a field from the entire JVM. Private members of a class are accessible from other instances of the same class — this is why a copy constructor can read other.privateField directly.

Constructors

FresherDefault vs parameterized constructor — what is the difference and what are the rules?

A default constructor takes no arguments. The compiler automatically provides one (with no body) only if you define no constructors. A parameterized constructor takes arguments to initialise fields at creation time.

Java 
class Point {
    int x, y;
    // No constructor defined → compiler inserts: Point() { super(); }
}

class Point3D {
    int x, y, z;

    // Parameterized constructor
    Point3D(int x, int y, int z) {
        this.x = x; this.y = y; this.z = z;
    }
    // NOTE: compiler does NOT insert a default constructor now.
    // Point3D p = new Point3D(); // COMPILE ERROR
}

class Point3DFull {
    int x, y, z;
    Point3DFull() { this(0, 0, 0); }            // explicit default — chains to parameterized
    Point3DFull(int x, int y, int z) { this.x = x; this.y = y; this.z = z; }
}
Common mistake: "The compiler always provides a default constructor." It provides one ONLY when you define no constructors at all. Define even one parameterized constructor and the no-arg default disappears.
MidExplain constructor chaining with this() and super(). What are the rules?

this(...) calls another constructor in the same class. super(...) calls a constructor in the parent class. Both must be the first statement in the constructor body and they are mutually exclusive within a single constructor.

Java 
class Employee {
    String name;
    int    id;
    double salary;

    Employee(String name, int id) { this(name, id, 50_000.0); } // chains to below
    Employee(String name, int id, double salary) {
        this.name   = name;
        this.id     = id;
        this.salary = salary;
    }
}

class Manager extends Employee {
    String department;

    Manager(String name, int id, String dept) {
        super(name, id, 90_000.0);  // MUST be first statement
        this.department = dept;
    }
}

Why it matters: Constructor chaining eliminates duplication by funneling all initialisation through a single canonical constructor. It is the Java equivalent of delegating constructors.

Interviewers listen for: The fact that super() is implicitly inserted by the compiler as the first statement if you write neither this() nor super() explicitly — as long as the parent has a no-arg constructor. If the parent only has parameterized constructors, failing to call super(...) explicitly is a compile error.
MidWhat is a copy constructor? Java vs C++.

A copy constructor creates a new object as a copy of an existing object. In C++ the compiler auto-generates one (shallow copy); in Java you write it manually.

Java 
class Address {
    String city;
    Address(String city) { this.city = city; }
    Address(Address other) { this.city = other.city; } // copy constructor
}

class Person {
    String  name;
    Address address; // mutable object — needs deep copy

    Person(String name, Address address) {
        this.name    = name;
        this.address = address;
    }

    // Copy constructor — deep copy to avoid aliasing
    Person(Person other) {
        this.name    = other.name;
        this.address = new Address(other.address); // deep copy
    }
}

Person p1 = new Person("Alice", new Address("London"));
Person p2 = new Person(p1); // deep copy
p2.address.city = "Paris";
System.out.println(p1.address.city); // still "London"
C++ 
class MyArray {
    int* data;
    int  size;
public:
    MyArray(int size) : size(size), data(new int[size]) {}
    // Auto-generated copy constructor does SHALLOW copy (copies pointer, not array!)
    // Rule of Three: if you define destructor, define copy constructor + copy assignment too
    MyArray(const MyArray& other) : size(other.size), data(new int[other.size]) {
        std::copy(other.data, other.data + size, data); // deep copy
    }
    ~MyArray() { delete[] data; }
};
SeniorExplain initializer blocks, the full order of initialization, and why constructors cannot be virtual.

Java initialises an object in this exact order:

  1. Parent class is fully initialised first (recursively from Object down).
  2. Static fields and static initialiser blocks run once per class load, in textual order.
  3. Instance fields are set to defaults (0, null, false).
  4. Instance initialiser blocks and field initialisers run in textual order.
  5. Constructor body runs.
Java 
class Base {
    static { System.out.println("1. Base static block"); }
    { System.out.println("3. Base instance block"); }
    Base() { System.out.println("4. Base constructor"); }
}

class Child extends Base {
    static { System.out.println("2. Child static block"); }
    { System.out.println("5. Child instance block"); }
    Child() { System.out.println("6. Child constructor"); }
}

new Child(); // Output order: 1, 2, 3, 4, 5, 6

Why can't constructors be virtual? Virtual dispatch requires a vtable pointer (vptr) to be set up, but the vptr is only initialised during construction. At the moment a constructor runs, the object's vtable is not yet finalised. Making constructors virtual would create a chicken-and-egg problem. In C++, calling a virtual method from a constructor resolves to the base class version, not the derived — for exactly this reason.

Interviewers listen for (C++): "Why should destructors be virtual?" — because if you delete a derived object via a base pointer and the base destructor is not virtual, only the base destructor runs, leaking the derived part. Mark base class destructors virtual whenever polymorphism is used.
SeniorWhat is a private constructor used for?

A private constructor prevents instantiation from outside the class. Primary uses:

  1. Singleton pattern — only the class itself can create the single instance.
  2. Utility/helper classes — classes with only static methods (e.g., java.lang.Math) use a private constructor to prevent meaningless instantiation.
  3. Factory method pattern — force callers to use a named factory method instead of new.
  4. Builder pattern — the product class may expose only a Builder for construction.
Java 
// Utility class — prevent instantiation
public final class MathUtils {
    private MathUtils() { throw new AssertionError("Utility class"); }
    public static int square(int n) { return n * n; }
}

// Factory method forces named construction
public class Color {
    private final int r, g, b;
    private Color(int r, int g, int b) { this.r = r; this.g = g; this.b = b; }

    public static Color ofRGB(int r, int g, int b) {
        if (r < 0 || r > 255) throw new IllegalArgumentException();
        return new Color(r, g, b);
    }
    public static Color RED   = ofRGB(255, 0, 0);
    public static Color GREEN = ofRGB(0, 255, 0);
}

SeniorExplain RAII and Java's equivalent: try-with-resources.

RAII (Resource Acquisition Is Initialisation) is a C++ idiom: tie a resource's lifetime to an object's lifetime. Acquire in the constructor; release in the destructor. Since destructors run deterministically at scope exit, resources are always freed — even under exceptions.

Java's equivalent is try-with-resources (Java 7+), which calls close() on any AutoCloseable at block exit, in reverse declaration order.

Java 
// AutoCloseable resource
class DBConnection implements AutoCloseable {
    DBConnection(String url) { System.out.println("Connected: " + url); }
    void query(String sql) { System.out.println("Query: " + sql); }
    @Override public void close() { System.out.println("Connection closed"); }
}

// try-with-resources: close() called automatically at block exit
try (DBConnection conn = new DBConnection("jdbc:mysql://localhost/db")) {
    conn.query("SELECT * FROM users");
} // conn.close() called here — guaranteed even if query() throws

// Multiple resources — closed in REVERSE order (conn2 first, then conn1)
try (DBConnection conn1 = new DBConnection("db1");
     DBConnection conn2 = new DBConnection("db2")) {
    // use both
}
Common mistake: Using finally instead of try-with-resources and forgetting that the close() itself might throw, masking the original exception. try-with-resources handles this correctly with suppressed exceptions.
MidStack vs heap memory. How does Java's garbage collector work at a high level?

Interviewers listen for: The distinction between reachability (not reference count). Java uses a tracing collector, not reference counting, so circular references are handled correctly.

MidIS-A vs HAS-A — when to use inheritance vs composition?

IS-A (inheritance): use when a subclass genuinely is a specialised kind of the superclass. The subclass must be substitutable for the superclass (Liskov Substitution Principle).

HAS-A (composition): use when one class contains or uses another class as a component.

// BAD: inheritance breaks encapsulation — Stack should NOT extend Vector
// java.util.Stack lets you call add(0, element) which violates stack semantics

// GOOD: composition — Stack uses Deque as its storage
class MyStack<T> {
    private final Deque<T> deque = new ArrayDeque<>(); // HAS-A

    public void push(T item) { deque.push(item); }
    public T    pop()        { return deque.pop(); }
    public T    peek()       { return deque.peek(); }
    public boolean isEmpty() { return deque.isEmpty(); }
    // Only stack operations exposed — no accidental access to queue methods
}
SeniorWhat is the diamond problem? How do Java and C++ each solve it?

The diamond problem arises in multiple inheritance when a class inherits from two classes that share a common ancestor. The question: which version of the ancestor's method/field should the descendant inherit?

A (method: speak()) / \ B C (both override speak()) \ / D ← which speak() does D inherit?

Java's solution: Classes can only extend one class. Interfaces can be multiply implemented. If two interfaces provide conflicting default methods, the implementing class must override and explicitly choose.

Java 
interface A { default String name() { return "A"; } }
interface B extends A { default String name() { return "B"; } }
interface C extends A { default String name() { return "C"; } }

class D implements B, C {
    // MUST override — ambiguity between B.name() and C.name()
    @Override public String name() {
        return B.super.name(); // explicitly select B's version
    }
}

C++'s solution: Virtual inheritance. Without it, D has two copies of A (one via B, one via C). With virtual inheritance, only one shared copy of A exists.

C++ 
struct A { virtual void speak() { std::cout << "A"; } };
struct B : virtual A { void speak() override { std::cout << "B"; } };
struct C : virtual A { void speak() override { std::cout << "C"; } };
struct D : B, C {
    void speak() override { B::speak(); } // disambiguate explicitly
    // Without 'virtual' above, D would have TWO copies of A's data
};
SeniorExplain Python's MRO and the C3 linearization algorithm.

Python supports multiple inheritance. The Method Resolution Order (MRO) determines which class's method is called first. Python uses the C3 linearization algorithm (since Python 2.3) to compute a consistent, predictable linear order.

Rule of thumb: MRO follows a depth-first, left-to-right order, but never revisits a class until all its subclasses have been visited. The result is checked via ClassName.__mro__.

Python 
class A:
    def hello(self): return "A"

class B(A):
    def hello(self): return "B"

class C(A):
    def hello(self): return "C"

SeniorHow does the JVM implement runtime polymorphism? Explain vtable and dynamic dispatch.

The JVM (and C++) implement dynamic dispatch using a virtual method table (vtable):

  1. Each class has a vtable — an array of pointers to its virtual method implementations.
  2. Each object has a hidden vptr (virtual pointer) pointing to its class's vtable.
  3. When you call a virtual method on an object reference, the JVM follows the vptr → vtable → method pointer, then calls that method. This is one pointer indirection.
Object in heap: ┌──────────────────┐ │ vptr ──────────►│Dog vtable │ name = "Rex" │ [0] breathe → Animal::breathe │ speed = 10 │ [1] speak → Dog::speak ← overridden └──────────────────┘ [2] fetch → Dog::fetch Animal ref = new Dog("Rex"); ref.speak() → vptr → vtable[1] → Dog::speak() → "Woof"

JIT optimisation: The JVM's JIT compiler can devirtualise calls when it can prove only one implementation exists (monomorphic call site), turning the virtual dispatch into a direct call — eliminating the overhead entirely.

MidWhen do you choose an abstract class over an interface, and vice versa?

Choose an abstract class when:

  • You want to share code (implementation) among closely related classes.
  • Subclasses need common non-public state (private/protected fields).
  • You expect future versions to add methods without breaking existing subclasses (via concrete methods).
  • You need constructors for initialisation logic.

Choose an interface when:

  • Unrelated classes need to implement the same capability (e.g., Comparable, Serializable).
  • You want to support multiple type inheritance.
  • You are defining a pure contract with no implementation sharing.
  • You want API stability with the ability to add default methods later without breaking existing implementors.
Real-world example: AbstractList (abstract class) provides skeletal implementation of List (interface). Custom list implementations extend AbstractList to get most list behaviour for free, implementing only get() and size(). This is the Template Method + Interface combination.
MidWhat are default methods in interfaces (Java 8+) and how do you resolve conflicts?

Java 8 added default methods to interfaces to allow interface evolution without breaking existing implementations. They have a body and are inherited by implementing classes.

Conflict resolution rules (3 rules, in priority order):

  1. Class wins: If a class (or superclass) provides a concrete implementation, it wins over any interface default.
  2. More specific interface wins: If interface B extends interface A and both provide a default, B's version wins.
  3. Must override: If neither rule above resolves the conflict, the implementing class must explicitly override and choose.
Java 
interface Flyable  { default String move() { return "fly";  } }
interface Swimmable{ default String move() { return "swim"; } }

class Duck implements Flyable, Swimmable {
    // MUST override — ambiguous between Flyable.move() and Swimmable.move()
    @Override public String move() {
        return Flyable.super.move() + "/" + Swimmable.super.move(); // "fly/swim"
    }
}

// Java 9: private interface methods for internal code sharing among defaults
interface Formatter {
    private String stripSpaces(String s) { return s.trim(); } // helper
    default String format(String s) { return stripSpaces(s).toUpperCase(); }
}

FresherWhat are static variables and static methods? What do they share?

Static members belong to the class, not to any particular object. All instances share one copy of a static variable; calling a static method does not require an instance.

Java 
class Counter {
    private static int instanceCount = 0; // shared across ALL instances
    private final int id;

    Counter() {
        instanceCount++;
        this.id = instanceCount;
    }

    static int getCount() { return instanceCount; } // no 'this' needed
    int getId()           { return id; }
}

Counter a = new Counter(); // instanceCount = 1
Counter b = new Counter(); // instanceCount = 2
System.out.println(Counter.getCount()); // 2 — called on the CLASS
System.out.println(a.getId());          // 1 — instance-specific

Common use cases: constants (static final), utility methods (no state needed), factory methods, shared counters/caches.

Common mistake: Referring to instance fields or this from a static method — compile error. Static methods cannot access instance state because they may be called without any object existing.
MidStatic binding vs dynamic binding — explain with examples.

Static binding (early binding): the compiler resolves the method call at compile time using the reference type. Applies to static, private, and final methods, and to overloaded methods.

Dynamic binding (late binding): the JVM resolves the call at runtime using the runtime type (actual object type). Applies to overridden instance methods.

Java 
class Parent {
    static void staticM() { System.out.println("Parent.static"); }
    void         dynM()   { System.out.println("Parent.dynamic"); }
}
class Child extends Parent {
    static void staticM() { System.out.println("Child.static"); }  // hiding
    @Override void dynM() { System.out.println("Child.dynamic"); } // overriding
}

Parent p = new Child();  // reference: Parent, runtime: Child

// STATIC BINDING — resolved by reference type (Parent)
p.staticM();  // "Parent.static"

// DYNAMIC BINDING — resolved by runtime type (Child)
p.dynM();     // "Child.dynamic"
MidWhy can't static methods use `this` or be overridden?

this is a reference to the current object. Static methods belong to the class, not an object — there is no "current object" in a static context, so this is meaningless.

Static methods can be hidden (re-declared in a subclass) but not overridden because override implies runtime dispatch via the vtable, which requires an object. Static methods are resolved via the class reference at compile time — they bypass the vtable entirely.

Java 
class Util {
    static int square(int n) {
        // this.something would be: ERROR — 'this' in static context
        return n * n;
    }
}

// static methods are not part of the virtual dispatch mechanism

MidAggregation vs Composition — what is the key practical difference?

The key differences are ownership and lifecycle:

  • Aggregation: The contained object is created outside and passed in. It can be shared (multiple containers may reference it) and continues to exist after the container is destroyed.
  • Composition: The container creates and owns the part. The part is not shared, and when the container is destroyed, the part is too.

In UML: aggregation uses a hollow diamond on the owner end; composition uses a filled diamond.

Interviewers listen for: The lifecycle test. Ask yourself "if the container object is deleted, does the contained object cease to make sense?" If yes: composition. If no: aggregation.
Common mistake: Conflating "aggregation" with "any HAS-A relationship." Composition IS-also-a HAS-A, but with ownership semantics. Not all HAS-A relationships are composition.

Object Methods & Contracts

MidExplain the equals/hashCode contract and common violations.

The contract (from java.lang.Object Javadoc):

  1. Consistent with equals: If a.equals(b) is true, then a.hashCode() == b.hashCode().
  2. Reflexive: a.equals(a) must be true.
  3. Symmetric: a.equals(b) == b.equals(a).
  4. Transitive: a.equals(b) && b.equals(c) implies a.equals(c).
  5. hashCode stability: Must return the same value on multiple calls during one JVM run (fields used must not change).
Java 
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;            // optimisation
        if (!(o instanceof Point)) return false; // null-safe, type-safe
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }

    @Override public int hashCode() {
        return 31 * x + y;  // same fields as equals — contract satisfied
    }
}

// VIOLATION — override equals but NOT hashCode:
// Map<Point, String> map = new HashMap<>();
// map.put(new Point(1, 2), "A");
// map.get(new Point(1, 2)); // returns null! Different hashCode → different bucket
Danger: Using a mutable object as a HashMap key. If the object is mutated after insertion, its hashCode changes, and the map can no longer find it. Prefer immutable keys or keys based on immutable fields.
Mid== vs .equals() in Java — what is the difference?

== compares references (memory addresses) for objects. It compares values for primitives.

.equals() compares logical equality as defined by the class. By default (Object's version), it behaves like ==; override it for value-based equality.

Java 
String s1 = new String("hello");
String s2 = new String("hello");

System.out.println(s1 == s2);        // false — different objects in memory
System.out.println(s1.equals(s2));   // true  — same character content

// String pool optimisation: string literals are interned
String s3 = "hello";
String s4 = "hello";
System.out.println(s3 == s4);        // true  — same pool reference (JVM detail)

Integer a = 127, b = 127;
System.out.println(a == b);          // true  — Integer cache: -128 to 127
Integer c = 128, d = 128;
System.out.println(c == d);          // false — outside cache range, new objects
Common mistake: Using == to compare String, Integer, or other wrapper types. Always use .equals() for object equality. The integer cache makes == work for small values (luring developers into a trap).

        copy.address = address.clone();       // deep clone the mutable part
        return copy;

Immutability & Value Objects

MidHow do you write a truly immutable class in Java? Walk me through the recipe.

An immutable object's state cannot change after construction. The recipe (6 rules):

  1. Declare the class final (prevent subclassing from adding mutable state).
  2. Make all fields private final.
  3. No setter methods.
  4. Initialise all fields in the constructor.
  5. Defensive copy mutable objects on the way in (constructor) and out (getters).
  6. If the class extends another class: the superclass must also be immutable or use composition.
Java 
import java.util.Date;
import java.util.Collections;
import java.util.List;
import java.util.ArrayList;

public final class ImmutableOrder {          // Rule 1: final class
    private final String   id;               // Rule 2: private final
    private final Date     createdAt;        // mutable! must copy
    private final List<String> items;       // mutable! must copy

    public ImmutableOrder(String id, Date createdAt, List<String> items) {
        this.id        = id;
        this.createdAt = new Date(createdAt.getTime()); // Rule 5: defensive copy IN
        this.items     = Collections.unmodifiableList(new ArrayList<>(items)); // copy IN
    }

    public String getId()           { return id; }
    public Date   getCreatedAt()    { return new Date(createdAt.getTime()); } // copy OUT
    public List<String> getItems() { return items; } // unmodifiable view — safe
}
// Alternative: use Java 16+ records (below), or java.time.LocalDate (inherently immutable)
MidWhat are Java records? How do they enforce immutability?

Records (Java 16+) are a concise way to declare immutable data carriers. The compiler auto-generates: private final fields, a canonical constructor, accessors, equals, hashCode, and toString.

Java 
// Equivalent to ~30 lines of boilerplate:
record Point(int x, int y) { }

// Usage
Point p = new Point(3, 4);
System.out.println(p.x());       // accessor (not getX()!)
System.out.println(p);           // "Point[x=3, y=4]"
Point p2 = new Point(3, 4);
System.out.println(p.equals(p2)); // true — value-based equality

// Compact canonical constructor for validation
record Range(int lo, int hi) {
    Range {  // compact constructor — parameters same as components
        if (lo > hi) throw new IllegalArgumentException(lo + " > " + hi);
    }
}

// Records are implicitly final; cannot extend other classes
// But CAN implement interfaces
Interviewers listen for: Records are not just syntactic sugar — they declare a new kind of Java type (a nominal tuple). They are ideal for DTOs, method return types with multiple values, and pattern matching.
MidWhy is immutability important? What are its benefits and costs?

Benefits:

  • Thread safety: Immutable objects can be shared freely across threads — no synchronisation needed.
  • Cache keys / HashMap keys: hashCode cannot change, so the object is safe as a key.
  • Failure atomicity: An object either gets constructed successfully or not at all — no partially-constructed state visible.
  • Simple reasoning: No surprise mutations; easier to track state changes.

Costs:

  • Creating a new object for every change (e.g., String concatenation in a loop). Use StringBuilder for repeated mutations.
  • GC pressure: more short-lived objects.

SOLID & Design Principles

SOLID questions appear in almost every mid-to-senior Java interview. Don't just define the principles — show code that violates them and code that fixes the violation.
MidWhat is coupling and cohesion? What is ideal?

Cohesion: How focused a module/class is on doing one thing well. High cohesion = class has a single, well-defined purpose.

Coupling: How dependent modules are on each other's internals. Low coupling = changing one module doesn't force changes in others.

Ideal: high cohesion + low coupling. High cohesion makes classes maintainable; low coupling makes the system modular and testable.

Principle: A class should have only one reason to change. It should be responsible for one actor.

MidL — Liskov Substitution Principle (LSP). What makes it tricky?

Principle: Objects of a supertype must be replaceable with objects of any subtype without altering the correctness of the program. Subtypes must honour the contract of the supertype.

The classic violation: Square extends Rectangle — setting width and height independently is valid for Rectangle but breaks Square's invariant.

Java 
// VIOLATION: Square IS-A Rectangle? Mathematically yes; behaviourally NO
class Rectangle {
    int width, height;
    void setWidth(int w)  { this.width  = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}
class Square extends Rectangle {
    @Override void setWidth(int w)  { this.width = this.height = w; } // breaks LSP!
    @Override void setHeight(int h) { this.width = this.height = h; }
}

// Client code that works for Rectangle but NOT for Square:
void resize(Rectangle r) {
    r.setWidth(4); r.setHeight(5);
    assert r.area() == 20; // fails for Square (area = 25)
}

// FIX: don't inherit — use a common interface or separate hierarchy
interface Shape2D { int area(); }
class Rectangle2 implements Shape2D { int w, h; public int area(){return w*h;} }
class Square2     implements Shape2D { int s;    public int area(){return s*s;} }

MidWhat are generics? Explain bounded type parameters.

Generics allow classes and methods to operate on types specified as parameters, providing compile-time type safety without casting.

Java 
// Generic class
class Box<T> {
    private T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
}

Box<String>  strBox = new Box<>("hello");
Box<Integer> intBox = new Box<>(42);
// strBox.get().length()  → OK — no cast needed
// intBox.get().length()  → COMPILE ERROR — Integer has no length()

// Bounded type parameter
<T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}
// max("apple", "banana") → "banana"
// max(3, 7)              → 7
// max(new Object(), ...) → COMPILE ERROR — Object doesn't extend Comparable
SeniorWhat is type erasure? What are its practical consequences?

Java generics are implemented via type erasure: type parameters are erased at compile time, replaced with their upper bounds (Object if unbounded). At runtime, no generic type information exists in the bytecode.

Consequences:

  1. List<String> and List<Integer> are the same class at runtime (List).
  2. Cannot use instanceof with parameterized types: obj instanceof List<String> is illegal.
  3. Cannot create generic arrays: new T[10] is illegal.
  4. Cannot create instances of type parameters: new T() is illegal.
  5. No overloading based solely on type parameter: void foo(List<String> l) and void foo(List<Integer> l) is a compile error — same erasure.
Java 
// At runtime, these are the SAME type:
List<String>  ls = new ArrayList<>();
List<Integer> li = new ArrayList<>();
System.out.println(ls.getClass() == li.getClass()); // true

// Workaround: pass Class<T> token
class TypedRepo<T> {
    private final Class<T> type;
    TypedRepo(Class<T> type) { this.type = type; }
    T create() throws Exception { return type.getDeclaredConstructor().newInstance(); }
}
TypedRepo<User> repo = new TypedRepo<>(User.class);
SeniorCovariance, contravariance, and invariance. Explain wildcards.

Invariant: List<Cat> is NOT a subtype of List<Animal> — generics are invariant by default.

Covariant: ? extends T — accepts T and any subtype. Read-only (producer). Arrays are covariant (Cat[] is-a Animal[]) — this can cause ArrayStoreException at runtime.

Contravariant: ? super T — accepts T and any supertype. Write-only (consumer).

Mnemonic: PECS — Producer Extends, Consumer Super.

Java 
// copy elements from src (producer) into dst (consumer)
static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T t : src) dst.add(t);
}

List<Cat>    cats = List.of(new Cat());
List<Animal> zoo  = new ArrayList<>();
copy(cats, zoo);  // Cat extends Animal: src=? extends Animal, dst=? super Cat → OK

// Without wildcards you'd need:
// copy(List<T> src, List<T> dst) — cannot pass List<Cat> where List<Animal> expected

MidJava exception hierarchy — checked vs unchecked. When should you use each?
Throwable ├── Error (don't catch — JVM/system errors) │ ├── OutOfMemoryError │ ├── StackOverflowError │ └── AssertionError └── Exception ├── RuntimeException ← UNCHECKED (don't need to declare/catch) │ ├── NullPointerException │ ├── IllegalArgumentException │ ├── IndexOutOfBoundsException │ └── ClassCastException └── (others) ← CHECKED (must declare throws or catch) ├── IOException ├── SQLException └── ParseException

Checked exceptions: Use when the caller can reasonably recover from the error and it is part of the API contract (e.g., file not found — caller can prompt user to choose another file).

Unchecked (RuntimeException): Use for programming errors and unrecoverable conditions (null where not expected, invalid argument, logic errors). They signal bugs, not expected conditions.

Interviewers listen for: "Checked exceptions are for recoverable conditions; unchecked for programming errors." Also worth mentioning: the trend in modern Java/frameworks (Spring, Jakarta) is to prefer unchecked exceptions — wrapping checked exceptions reduces boilerplate without sacrificing error handling.
MidWhat are the rules for overriding methods that throw exceptions?

The overriding method can:

  • Throw fewer or narrower checked exceptions than the overridden method.
  • Throw no checked exceptions.
  • Throw unchecked exceptions freely.

It CANNOT throw broader or new checked exceptions not declared by the overridden method. This preserves the Liskov Substitution Principle: callers that catch the parent's exceptions will still have their catches satisfied.

Java 
class Parent {
    void readFile() throws IOException, ParseException { }
}
class Child extends Parent {
    @Override void readFile() throws IOException { }    // OK: narrower (dropped ParseException)
    // @Override void readFile() throws Exception { }  // ILLEGAL: broader (Exception ⊃ IOException)
    // @Override void readFile() throws SQLException {} // ILLEGAL: new checked exception
    // @Override void readFile() throws RuntimeException {} // OK: unchecked, always allowed
}
MidHow does try-with-resources handle suppressed exceptions?

If an exception is thrown in the try block AND another exception is thrown by close(), the close() exception is added as a suppressed exception on the primary exception. It is not swallowed, and it does not replace the primary exception.

Java 
class NoisyResource implements AutoCloseable {
    @Override public void close() throws Exception {
        throw new Exception("close failed");
    }
}

try (NoisyResource r = new NoisyResource()) {
    throw new RuntimeException("try body failed"); // primary
} catch (RuntimeException e) {
    System.out.println(e.getMessage());             // "try body failed"
    Throwable[] suppressed = e.getSuppressed();
    System.out.println(suppressed[0].getMessage()); // "close failed" — preserved!
}

// is LOST — you only see the finally exception. try-with-resources is strictly better.

SeniorSingleton pattern — all implementation variants and pitfalls.

Singleton ensures a class has exactly one instance. Multiple implementation variants — each solves different problems:

Java 
// 1. EAGER: simple, thread-safe; instance created even if never used
class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() { return INSTANCE; }
}

// 2. LAZY + DOUBLE-CHECKED LOCKING: thread-safe, lazy, fast after init
class DCLSingleton {
    private static volatile DCLSingleton instance; // volatile is REQUIRED
    private DCLSingleton() {}
    public static DCLSingleton getInstance() {
        if (instance == null) {                    // first check (unsynchronised)
            synchronized (DCLSingleton.class) {
                if (instance == null) {            // second check (inside lock)
                    instance = new DCLSingleton();
                }
            }
        }
        return instance;
    }
}

// 3. ENUM: best practice (Bloch) — serialization-safe, reflection-safe
enum EnumSingleton {
    INSTANCE;
    public void doWork() { System.out.println("Working..."); }
}
EnumSingleton.INSTANCE.doWork();

// 4. INITIALIZATION-ON-DEMAND HOLDER: thread-safe without volatile/sync
class HolderSingleton {
    private HolderSingleton() {}
    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }
    public static HolderSingleton getInstance() { return Holder.INSTANCE; }
    // Class loaded lazily on first call to getInstance(); JVM guarantees thread-safety
}
Pitfalls: Without volatile, DCL is broken (memory model). Reflection can break Singleton by calling private constructor (enum prevents this). Serialization creates a new instance unless you add readResolve().

Anti-Patterns

MidGod Object, Spaghetti Inheritance, and Yo-Yo Problem.

God Object (God Class): A single class that knows too much and does too much — low cohesion, high coupling. Symptoms: hundreds of fields and methods, imports everything, impossible to test in isolation.

Fix: Apply SRP. Extract cohesive clusters into focused classes.

Spaghetti Inheritance: Deep, tangled inheritance hierarchies (e.g., 8-level chains) that are impossible to reason about. Overriding methods at random depths causes unexpected behaviour. Every change in the hierarchy ripples unpredictably.

Fix: Flatten hierarchies. Prefer composition. Cap inheritance depth at 2-3 for application code.

Yo-Yo Problem: Understanding a method's behaviour requires constantly jumping ("yo-yoing") up and down a deep inheritance chain. You can't understand a method without reading 5 ancestors.

Fix: Composition + explicit delegation. Keep behaviour visible in the class where it's used.

MidFragile Base Class, Singleton Overuse, and Tight Coupling.

Fragile Base Class: A superclass that breaks subclasses when modified, even if the modification seems safe. Caused by exposing too much in the base class that subclasses depend on.

Fix: Design for extension or prohibit it (make class/method final). Document what subclasses may and may not override. Prefer composition.

Singleton Overuse: Using Singleton as a global variable dressed up in a pattern. Problems: hidden dependencies, impossible to unit test (can't mock), threading issues, violates SRP.

Fix: Inject dependencies explicitly (DIP). Use frameworks (Spring, CDI) for lifecycle management instead of manual Singletons.

Tight Coupling: Classes depend on concrete implementations rather than abstractions. Changing one class requires changing many others.

Fix: Program to interfaces. Use dependency injection. Apply DIP.

MidPrimitive Obsession and Feature Envy.

Primitive Obsession: Using primitives/strings where a dedicated class would be clearer. E.g., storing a phone number as String, a monetary value as double, or user role as int.

Fix: Extract dedicated value objects: PhoneNumber, Money, UserRole enum. These encapsulate validation and domain logic.

Feature Envy: A method that seems more interested in data from another class than its own. It calls many methods of another class to do its work.

Fix: Move the method to the class whose data it uses. Follow the Law of Demeter.

Language-Specific Gotchas

SeniorJava OOP gotchas every senior dev must know.
  • Calling overridden methods from a constructor: During construction, the vtable points to the subclass method even though the subclass hasn't been initialised yet. This can cause NullPointerExceptions or incorrect initial state.
  • equals() with null: null.equals(x) throws NPE; "string".equals(null) is safe and returns false. Always put the known non-null value first.
  • Autoboxing in collections: Map<Integer,Integer> m; m.remove(key) where key is int calls remove(int index) not remove(Object key) on certain collections. Cast explicitly.
  • Covariant arrays: Integer[] ints = new Integer[3]; Object[] objs = ints; objs[0] = "hello"; compiles but throws ArrayStoreException at runtime.
Java 
// CALLING OVERRIDDEN METHOD FROM CONSTRUCTOR — dangerous!
class Base {
    Base() { init(); }       // 'init' is overridden...
    void init() { System.out.println("Base.init"); }
}
class Derived extends Base {
    private int value = 10;  // not yet assigned when Base() calls init()
    @Override void init() { System.out.println("value = " + value); } // prints 0!
    // Java default-initialises int fields to 0 BEFORE running constructors
}
new Derived(); // prints "value = 0", not "value = 10" — a common trap
SeniorC++ OOP gotchas — the rule of three/five/zero.

Rule of Three: If you define any of destructor, copy constructor, copy assignment operator — define all three. Managing raw resources in one implies you need to manage them in all.

Rule of Five: Rule of Three + move constructor + move assignment operator. Modern C++11+ adds move semantics.

Rule of Zero: Best practice — avoid managing resources directly; use smart pointers (unique_ptr, shared_ptr) so the compiler-generated defaults work correctly and you need none of the five.

    // No resource management needed in this class at all

Rapid-Fire Q&A, Puzzles & LLD Prompts

FresherRapid-fire: Core OOP Definitions (10 questions)
  1. What is the difference between an abstract class and an interface? — Abstract class can have state and constructors; interface cannot (except default/static methods). A class can implement many interfaces but extend only one class.
  2. Can abstract classes have constructors? — Yes. Called via super() from subclass constructors. They cannot be instantiated directly.
  3. Can an interface extend multiple interfaces? — Yes. interface C extends A, B is legal in Java.
  4. What is the difference between method hiding and method overriding? — Overriding: instance methods, resolved by runtime type (dynamic dispatch). Hiding: static methods, resolved by reference type (static binding).
  5. Can you override a private method? — No. Private methods are not visible to subclasses; any same-named method in a subclass is a new method, not an override.
  6. What happens if you don't define hashCode() when you override equals()? — HashMap/HashSet will fail: equal objects may fall in different buckets, making lookups return null for objects that were inserted.
  7. Is String immutable in Java? Why? — Yes. final class, private final char array, no setters. Enables String pool, thread-safety, safe use as HashMap key.
  8. What is the difference between Comparable and Comparator? — Comparable: natural order, implemented by the class itself (compareTo). Comparator: external, custom ordering (compare), can have many.
  9. Can constructors be synchronized? — No. An object under construction is not visible to other threads unless you publish the reference (which you shouldn't do from a constructor). The JVM ensures only one thread constructs an object.
  10. What is the default value of a boolean field in Java? — false. Default values: int=0, double=0.0, char='', Object=null.
MidRapid-fire: Polymorphism & Inheritance (10 questions)
  1. What is covariant return type? — An overriding method can return a subtype of the superclass method's return type. E.g., parent returns Animal, child can return Dog.
  2. Can you have a static abstract method? — No. Abstract implies the method must be overridden by subclasses; static methods cannot be overridden.
  3. What is the output of new Child() if Child extends Parent and both have System.out.println in constructors? — Parent's constructor runs first (via implicit super()), then Child's.
  4. What is the diamond problem? — Ambiguity when a class inherits from two classes that share a common ancestor. Java avoids this for classes (single inheritance) but handles it for interfaces via explicit disambiguation.
  5. Can you instantiate an anonymous class? — Yes — that is precisely what the anonymous class syntax does. new Runnable() { ... } creates one instance of the anonymous class.
  6. What is an upcast vs a downcast? — Upcast: subtype to supertype (always safe, implicit). Downcast: supertype to subtype (risky, explicit, throws ClassCastException if wrong). Use instanceof before downcasting.
  7. Does Java support multiple inheritance of state? — No. You cannot have multiple parent classes (and thus multiple sets of state). Interface default methods share behaviour but not state (no instance fields).
  8. What is the difference between compile-time and runtime exceptions? — Compile-time: compiler requires you handle/declare checked exceptions. Runtime (unchecked): RuntimeException subclasses, no compiler enforcement.
  9. What happens when you call a virtual method on a null reference in C++? — Undefined behaviour. The vtable lookup itself requires following the vptr in the object's memory, which is not there for null. In Java: NullPointerException at the call site.
  10. Can you override equals() to return true for objects of different types? — You can, but it violates the symmetry requirement: if a.equals(b) is true, b.equals(a) must also be true. Different classes rarely satisfy this.
SeniorRapid-fire: Design & Architecture (10 questions)
  1. What is the difference between Factory Method and Abstract Factory? — Factory Method: one product, subclasses decide implementation. Abstract Factory: family of related products, ensures consistency across the family.
  2. Why is the Singleton pattern considered an anti-pattern? — Global state, hidden dependencies, prevents unit testing (can't mock), threading issues, violates SRP (manages its own lifecycle).
  3. What is the Dependency Injection pattern? — Providing dependencies from outside rather than creating them inside. Enables testing (mock injection), flexibility (swap implementations), and adheres to DIP.
  4. Explain the Open/Closed Principle in one sentence. — Open for extension (add new behaviour via new classes), closed for modification (don't change existing working code).
  5. What does "program to an interface, not an implementation" mean? — Declare variables/parameters using the interface/abstract type rather than concrete class. Allows swapping implementations without changing dependent code.
  6. What is the difference between cohesion and coupling? — Cohesion: how related the responsibilities of a class are (high = good). Coupling: how much one class depends on another's internals (low = good).
  7. What is the purpose of the Repository pattern? — Abstracts data access behind a collection-like interface. Business logic uses the interface; the implementation may be in-memory, SQL, or NoSQL.
  8. What is an aggregate root in DDD? — The single entry point for a cluster of domain objects (aggregate). All external references point to the root; internal objects are not accessible directly.
  9. What is the difference between Strategy and Template Method? — Template Method: variation through inheritance (hooks defined in subclass). Strategy: variation through composition (algorithm swapped by injecting different Strategy object).
  10. What is the Facade pattern and when would you use it? — Provides a simple interface to a complex subsystem. Use it to reduce the complexity visible to clients of a library or module.
MidRapid-fire: SOLID Quick Round (10 questions)
  1. Which SOLID principle does having one method per class satisfy? — SRP, loosely — but SRP is about one reason to change, not number of methods.
  2. Name a violation of LSP in Java's own standard library. — java.util.Stack extends Vector. Stack supports LIFO operations, but Vector adds index-based access that violates the Stack contract.
  3. How do default methods in interfaces relate to OCP? — They allow adding new behaviour to an interface without breaking existing implementors — extending the contract while being closed for modification of implementors.
  4. What is the "interface segregation" problem? — Clients are forced to depend on interfaces with methods they don't use. Causes: fat interfaces, dummy implementations that throw UnsupportedOperationException.
  5. High-level module vs low-level module in DIP? — High-level: business logic (what to do). Low-level: infrastructure (how to do it, e.g., database, email). Both should depend on an abstraction (interface).
  6. How does Spring enforce DIP? — Via dependency injection (constructor/setter/field injection). The container wires implementations to interfaces; high-level beans declare interfaces, not implementations.
  7. What is "fragile base class" in context of OCP? — A base class that breaks subclasses when changed — the base class is not truly closed for modification from the subclass's perspective.
  8. Does DRY mean no code duplication at all? — No. DRY is about knowledge duplication, not syntactic duplication. Sometimes two similar code snippets encode different domain rules and should remain separate.
  9. What is a "leaky abstraction"? — An abstraction that exposes details of its implementation to callers. E.g., a SQL query library that throws SQLException to callers who don't know about SQL.
  10. Name a real-world example of the Dependency Inversion Principle. — JDBC: application code uses the java.sql.Connection interface; the MySQL JDBC driver provides the implementation. Swapping drivers requires zero application code changes.

Puzzle 1:

class A { int val = 1; int get() { return val; } }
class B extends A { int val = 2; @Override int get() { return val; } }

System.out.println(obj.val);     // ?

Methods ARE polymorphic — obj.get() dispatches to B.get() at runtime, returning B's val=2.

Puzzle 3:

Java 
class Parent {
    Parent() { show(); }                    // called during construction
    void show() { System.out.println("Parent.show"); }
}
class Child extends Parent {
    private int x = 42;
    @Override void show() { System.out.println("Child.show x=" + x); }
}
new Child();
Output: Child.show x=0
When Parent() runs, Child's vtable is already set (pointing to Child.show), so Child.show() is called.
But Child's field initialiser (x = 42) hasn't run yet — fields default to 0 during super-construction.
This is the "calling overridden method from constructor" trap.
