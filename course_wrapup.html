Hybrid-Search RAG with Citation Verification

Course wrap-up & interview guide — every method, sample I/O, and questions you'll get asked.

A production-shaped Retrieval-Augmented Generation system: dense (semantic) + sparse (BM25) retrieval, fused with Reciprocal Rank Fusion, reranked cross-encoder–style, answered with grounded per-sentence citations, and — the differentiator — an independent verification pass that checks every citation actually supports its claim. Built in Python + LangChain + Google Gemini.

★ How to pitch this project to an interviewer

Three lengths — pick based on how much room they give you. Start short; expand if they lean in.

The 30-second version (the opener)

"I built a hybrid-search RAG system with citation verification from scratch. It answers questions over a document corpus by combining two kinds of retrieval — semantic vector search and keyword BM25 — fusing the results, reranking them with a cross-encoder-style pass, and generating an answer with per-sentence citations. The part I'm most proud of is the verification layer: after the model writes a cited answer, an independent check confirms each cited source actually supports its claim — which is the step most RAG systems skip, and it's what makes the citations trustworthy instead of decorative."

The 2-minute version (problem → approach → differentiator → learning)

The problem: "A plain LLM hallucinates, doesn't know your private documents, and can't cite sources. RAG fixes that by retrieving relevant text and making the model answer from evidence — but most RAG demos stop at 'embed, search, stuff into prompt,' which fails on exact-term queries and still produces confident, unverifiable answers."

My approach: "So I built the full production shape. I chunk documents structure-first so each chunk is one topic with provenance metadata. I index them two ways — dense Gemini embeddings for meaning, and BM25 for exact terms like error codes that embeddings blur. I fuse the two rankings with Reciprocal Rank Fusion, which merges by rank position so their incompatible score scales don't fight. Then a cross-encoder-style reranker reads the query and each candidate together to get precision at the top, and the generator writes a grounded answer with [n] citations."

The differentiator: "The key layer is verification. A citation the generator writes about itself is just a self-report. So a separate, independent judge sees only each claim and its cited passage and confirms entailment — failing closed, so an unverified claim is flagged rather than trusted. I proved it by injecting a plausible false claim; retrieval and generation both passed it through, and only the verifier caught it."

What I learned: "I evaluate retrieval and generation separately with recall@k, MRR, and faithfulness, and I added production optimizations I hit the need for live — a persistent embedding cache and parallelized reranking. The biggest lesson was that retrieval recall is the ceiling: no reranker or LLM fixes a chunk that was never retrieved."

If they say "walk me through the architecture"

Trace the pipeline in order — point at each stage and give its one job:

Chunk (one topic + provenance) → dense index (meaning) + BM25 (exact terms) → RRF fusion (scale-safe merge) → rerank (precision on a shortlist) → generate (grounded + cited) → verify (independent entailment per claim) → evaluate (measure each stage). Then land the framing: "cheap wide retrieval for recall, expensive narrow reranking for precision, and an independent verifier for trust."

Why this project stands out (if asked "why is it interesting?")

  • It's not a demo. Hybrid retrieval, fusion, reranking, verification, and evaluation — the layers tutorials skip.
  • Verification is rare. Independent, fail-closed citation checking is a genuine trust/safety layer most teams don't build.
  • Built from scratch. No black-box framework magic — I can explain every design decision and tradeoff.
  • Production-aware. I hit and handled real walls: rate limits (backoff + throttle), caching, parallelism, graceful degradation, and I can articulate what swaps out at scale (ANN vector DB, Elasticsearch, incremental indexing).
One-sentence summary to memorize: "A hybrid-retrieval RAG that combines semantic and keyword search, reranks for precision, generates grounded cited answers, and independently verifies every citation — so the answers are not just fluent, but provably backed by sources."

1 · Architecture & mental model

RAG in one line: instead of the LLM answering from memory, we retrieve relevant text from our own documents and make the model answer from that evidence — then we prove each sentence is backed by a source.

Two phases:

  • Indexing (offline, once): documents → chunks → two indexes (dense vectors + BM25).
  • Query (online, per request): retrieve from both → fuse → rerank → generate → verify.
QUERY │ ├─► dense_index.search() (semantic / meaning) ┐ └─► sparse_index.search() (BM25 / exact terms) ┘ │ fusion.reciprocal_rank_fusion() ← merge by RANK (scale-safe) │ rerank.rerank() ← cross-encoder-style precision, on a shortlist │ generation.generate_answer() ← grounded answer + [n] citations │ verification.verify_answer() ← INDEPENDENT entailment check per claim │ trustworthy answer + verified citations
Mental model: a research librarian who searches two ways, pulls the best few sources to the top, writes a cited answer, and then has a fact-checker read behind them to confirm every claim.

The #1 principle: retrieval recall is the ceiling on everything. You can't rerank, generate from, or cite a chunk that was never retrieved.

2 · chunking.py — documents → retrieval-ready chunks

Splits documents so each chunk is one focused topic with provenance metadata. Chunk quality is the ceiling on both retrieval and citation precision.

Chunk dataclass

The data contract for one retrieval unit — flows through every downstream stage.

Chunk(text, source, chunk_index, start_char, metadata)
Fieldstext the passage · source filename (citation label) · chunk_index globally-unique id · start_char offset · metadata section header

load_corpus(corpus_dir) → list[(filename, text)]

Ingestion layer. Reads every .md/.txt with explicit utf-8 (Windows-safe). Filename travels with text so provenance is never lost.

Inputa directory path
Output[('aurora_router_manual.md', '# Aurora X1...'), ('wifi_concepts.md', '# Understanding...')]

chunk_document(filename, text) → list[Chunk]

Two-stage split: (1) MarkdownHeaderTextSplitter cuts on #/##/### so no chunk mixes topics; (2) RecursiveCharacterTextSplitter (size 800, overlap 120) splits any oversized section for sharp embeddings. chunk_index=len(chunks) keeps ids globally unique.

3 · dense_index.py — semantic retrieval

Embeds chunks into vectors and searches by meaning. Strong on paraphrase, weak on exact tokens. Includes a persistent embedding cache.

embed_text(text, task_type) → list[float]

One text → one 3072-dim vector via Gemini. task_type is RETRIEVAL_DOCUMENT at index time, RETRIEVAL_QUERY at search time (Gemini optimizes each role). Checks a persistent cache first — hit → no API call.

Input("Error code E-4021 means...", "RETRIEVAL_DOCUMENT")
Output[-0.0065, 0.0235, -0.0096, ...] — length 3072, vector norm = 1.0 (unit vector)

build_index(chunks) → (np.ndarray, list[Chunk])

Embeds all chunks as documents, stacks into a float32 matrix, persists the cache. Returns matrix + chunks paired (row i ↔ chunks[i]).

Outputmatrix shape (9, 3072) dtype float32, plus the 9 chunks

search(query, matrix, chunks, top_k) → list[(score, Chunk)]

Embeds the query, computes matrix @ query_vec (dot product = cosine, since vectors are unit-norm) — one score per chunk in a single vectorized op — sorts descending.

Input"what does error code E-4021 mean"
Output
[(0.7963, Chunk #3 Error Codes),
 (0.6424, Chunk #4 Factory Reset),
 (0.6250, Chunk #2 Status Lights)]   ← note: fuzzy spread, everything "router-ish" scores 0.6+

_cache_key / _load_cache / _save_cache production

Persistent embedding cache. Key = sha256(model + task_type + text) → so changing the model auto-invalidates. Stored as a pickle in data/index/. Result: 5.2s cold → 0.0s warm, 9 API calls → 0.

Interview: "Dense retrieval matches meaning via cosine similarity over Gemini embeddings. I cache embeddings by content hash so unchanging chunks are never re-embedded — big latency, cost, and rate-limit win."

4 · sparse_index.py — BM25 keyword retrieval

Exact-term matching with IDF weighting + length normalization. Nails codes/names/jargon that embeddings blur.

tokenize(text) → list[str]

Lowercase + \w+ regex. Must be identical at index and query time — asymmetric tokenization is the #1 BM25 bug.

Input"What does error code E-4021 mean?"
Output['what','does','error','code','e','4021','mean']

build_bm25_index(chunks) → BM25Okapi

Tokenizes all chunks and builds the index, precomputing IDF + doc lengths at build time.

OutputBM25Okapi(corpus_size=9, avgdl=58.8)

search(query, bm25, chunks, top_k) → list[(score, Chunk)]

Tokenizes query, scores all chunks. Rare tokens (high IDF) dominate; chunks with no overlap score exactly 0.

Input"what does error code E-4021 mean"
Output
[(9.2954, Chunk #3 Error Codes),   ← rare token '4021' (IDF high) lives only here
 (0.0000, Chunk #0),
 (0.0000, Chunk #1),
 (0.0000, Chunk #2)]                ← razor-sharp separation vs dense's fuzzy 0.6s
Interview: "BM25 scores exact-term overlap with IDF and length normalization. Dense finds docs that mean the same thing; BM25 finds docs that say the same thing. I run both because each covers the other's blind spot."

5 · fusion.py — Reciprocal Rank Fusion

reciprocal_rank_fusion(result_lists, top_k) → list[(score, Chunk)]

Merges multiple ranked lists using score += 1/(RRF_K + rank) per chunk (RRF_K=60), keyed by source#index, summed across lists. Ignores raw scores — only rank position matters, so incompatible scales (cosine 0–1 vs BM25 unbounded) can't distort the merge. Takes a list of lists so it extends to N retrievers.

Input[dense_results, bm25_results]
LogicA: rank0 dense + rank1 bm25 = 1/60 + 1/61 = 0.03306 · C: rank2 + rank0 = 0.03280 · B: only in dense = 0.01639
Output[(0.03306, A), (0.03280, C), (0.01639, B)]
Interview: "RRF sums rank-based votes across retrievers. Agreement across both lifts a chunk to the top; a chunk found by only one retriever still survives (non-zero). k=60 dampens how much the very top ranks dominate. Crucially it's scale-independent — naive score addition would let BM25's unbounded scores swamp dense."

6 · rerank.py — cross-encoder-style reranking

Re-scores a shortlist by reading query + chunk together (unlike bi-encoder embeddings, which encode them separately). Runs after fusion, on few candidates, because each is an API call. Parallelized.

score_chunk(query, chunk) → float

Sends query + passage in one prompt asking a 0–10 relevance score. temperature=0 (deterministic/cacheable), max_output_tokens=5, defensive parse → 0.0 on any failure (never crash the pipeline).

Input("how do I fix E-4021", Chunk #3 Error Codes)
Output1.0 · same query vs Chunk #4 Factory Reset → 0.0

rerank(query, candidates, top_k) → list[(score, Chunk)]

Scores every candidate (discarding incoming RRF scores), sorts by the fresh score. Uses ThreadPoolExecutor(max_workers=5) + executor.map — concurrent I/O, order preserved, concurrency capped to respect rate limits.

Inputcandidate order [#4, #2, #3, #0] (answer buried at pos 3)
Output[(1.0, #3 Error Codes), (0.0, #4), (0.0, #2), (0.0, #0)] — #3 promoted to top
Perfsequential 3.57s → parallel 1.14s = 3.1× faster, identical ranking
Interview: "Retrieval optimizes recall (wide, cheap); reranking optimizes precision at the top (narrow, expensive). The cross-encoder reads query+chunk jointly, so it judges true relevance a bi-encoder can't. I parallelize the calls with a bounded thread pool since they're independent and I/O-bound."

7a · generation.py — grounded answer with citations

format_context(chunks) → str

Numbers chunks [1] (source #idx) text. That [n] is the thread that makes verification possible.

Output"[1] (aurora_router_manual.md #3) ...E-4021 means the router could not obtain an IP..."

generate_answer(query, chunks) → str

Grounding prompt with 3 rules: (1) use ONLY the passages, (2) cite [n] per sentence, (3) refuse with a fixed phrase if unanswerable. temperature=0.

Input"how do I fix E-4021?" + 3 chunks
Output"To resolve E-4021, power cycle the modem, wait sixty seconds, and then restart the Aurora X1 [1]."
Refusesquery "capital of France?" → "I don't have enough information to answer that."
Interview: "Grounding is prompt discipline plus traceable citations — the model reasons over provided evidence, not training memory, and refuses when the context lacks the answer."

7b · verification.py — the differentiator

Independently checks that every cited chunk actually entails its claim. A citation the generator writes about itself is a self-report; this is the proof.

parse_claims(answer) → list[Claim]

Splits answer into sentences (regex, punctuation lookbehind), extracts [n] numbers (\[(\d+)\] — digits only, so [abc] is ignored safely).

Input"To resolve E-4021... restart the Aurora X1 [1]."
Output[Claim(text='To resolve E-4021...', citations=[1])]

verify_claim(claim_text, chunk) → bool

Independent judge — sees ONLY the claim + its cited chunk (not the question, other chunks, or original answer). Strict YES/NO, temperature=0, fail-closed to False on any error.

Outputclaim vs Chunk #3 Error Codes → True · claim vs Chunk #4 Factory Reset → False

verify_answer(answer, chunks) → list[ClaimVerdict]

Parses claims, maps [n] → chunks[n-1] (bounds-checked against hallucinated [7]), verifies each. Uncited sentence → reason="no citation". Chunk list must be the SAME ordered list passed to generation.

Real answer[ClaimVerdict(supported=True, reason='supported')]
Injected lie"E-4021 means firmware corrupted, factory reset [1]" → supported=False, reason='not supported by cited passage' — caught
Interview: "The verifier is independent of the generator so it can't inherit its bias, and it fails closed — a false 'unverified' is safe, a false 'verified' is dangerous. This is the quality layer most RAG skips; it turns decorative citations into proven ones."

8 · evaluate.py — measure, don't eyeball

Retrieval and generation are measured separately, so a bad answer tells you which half broke.

recall_at_k(results, relevant_ids, k) → float

1.0 if a relevant chunk is in the top-k (set intersection), else 0.0. Measures the retrieval ceiling.

Exampleanswer at rank 2 → recall@1 = 0.0, recall@2 = 1.0

reciprocal_rank(results, relevant_ids) → float

1/position of first relevant hit. Measures how high — rewards reranking.

Examplerelevant chunk at rank 2 → 0.5

evaluate_retrieval(retriever, k) → (recall, mrr)

Averages both metrics over the golden EVAL_SET. Takes a retriever function so any config plugs in.

Output (real run)
Configuration     Recall@3     MRR
Dense only            1.00   1.000
BM25 only             1.00   0.900   ← slips on the paraphrase query (no exact token)
Hybrid (RRF)          1.00   1.000
Hybrid+Rerank         (rate-limited)
Interview: "Recall@k = did the right chunk reach the LLM; MRR = how high. Reranking should lift MRR while leaving recall flat. Faithfulness reuses the verifier — the guardrail and the metric are one machine. And a wrong golden label inverts the metric, so label quality is everything."

Meta-lesson: the architecture never changes at scale — only the implementation of each box. Because every stage sits behind a clean function boundary, scaling is a series of contained swaps (numpy → vector DB, rank-bm25 → Elasticsearch, script → service), not a rewrite.

Key design principles (say these out loud)

  • Retrieval recall is the ceiling — nothing downstream fixes a chunk that wasn't retrieved.
  • Chunk quality sets citation quality — structure-first splitting, provenance from day one.
  • Dense + sparse are complementary — meaning vs exact terms; hybrid covers both blind spots.
  • Never mix raw scores — RRF fuses on rank, which is scale-independent.
  • Recall then precision — cheap wide retrieval, then expensive narrow reranking on a shortlist.
  • Verification ≠ generation — an independent judge, fail-closed, is what makes citations trustworthy.
  • temperature=0 everywhere — deterministic → cacheable → reproducible.
  • Measure each stage separately — so you know which half broke.
  • Every external call can fail — cache, retry, parallelize, degrade gracefully.

Interview questions (with answers)

Click each to reveal a strong answer.

Architecture & fundamentals

What is RAG and why not just use a bigger LLM / long context?
RAG retrieves relevant text from your own corpus and puts it in the prompt so the model answers from evidence, not training memory. Long-context works for a small corpus but fails on scale (corpus exceeds the window), cost (you resend everything per query), latency, the "lost in the middle" effect, and observability (RAG makes retrieved evidence explicit and measurable).
Walk me through your pipeline end to end.
Chunk documents (structure-first) → index them two ways (dense Gemini embeddings + BM25) → retrieve from both → fuse with RRF → rerank a shortlist cross-encoder-style → generate a grounded answer with [n] citations → independently verify each claim against its cited chunk → return verified answer. Retrieval and generation are evaluated separately.
Why is "retrieval recall is the ceiling" the key idea?
Reranking, fusion, generation, and verification can only operate on chunks retrieval surfaced. A chunk never retrieved is invisible forever — so "use a better LLM" rarely fixes a bad RAG; the bug is usually upstream in retrieval.

Chunking & embeddings

How did you choose chunk size, and how does it affect citations?
Structure-first (markdown headers) so no chunk mixes topics, then a ~800-char size guard for sharp embeddings. Chunk size is the ceiling on citation precision — the chunk is the unit of verification, so a huge mixed chunk makes "supported by this chunk" a weak signal. Too small loses context; ~256–512 tokens with 10–20% overlap is a common production default.
What's the difference between a bi-encoder and a cross-encoder?
A bi-encoder (embeddings) encodes query and document separately into vectors compared by cosine — fast, precomputable, but lossy. A cross-encoder reads query and document together and outputs one relevance score — far more accurate but can't be precomputed, so it only runs on a shortlist at query time.
Why the RETRIEVAL_DOCUMENT vs RETRIEVAL_QUERY task types?
Gemini produces embeddings optimized per role; documents and queries get slightly different vectors tuned so queries match documents well. Using the wrong one silently hurts recall.
Why does dot product equal cosine similarity in your code?
Cosine = dot product divided by both norms. Gemini's full-3072-dim embeddings are unit-normalized (I verified norm = 1.0), so the denominator is 1 and dot product equals cosine. If I requested reduced dimensions they wouldn't be normalized and I'd have to normalize manually.

BM25 & fusion

What does BM25 catch that embeddings miss, and vice versa?
BM25 nails exact tokens — error codes, SKUs, names, rare jargon — because it matches literal terms with IDF weighting. It's blind to paraphrase. Embeddings catch meaning/synonyms but blur rare opaque tokens like E-4021 (no learned associations). Hybrid covers both.
Why RRF instead of just adding the two scores?
Dense scores are ~0–1; BM25 is unbounded and corpus-dependent. Adding them lets BM25 dominate arbitrarily. RRF discards raw scores and sums 1/(k+rank) — pure rank position — which is scale-independent, rewards cross-retriever agreement, and keeps single-retriever finds alive.
What does k=60 do in RRF?
It dampens how much the very top ranks dominate — the gap between rank 1 and rank 2 is small, so one lucky top hit can't swamp broad agreement. It's the standard value from the original RRF paper.

Reranking & generation

Where does the reranker sit and how many candidates?
After fusion, before generation, on a shortlist (~20–100 in production; I used ~5). Each candidate is a separate model call, so you never rerank the whole corpus — retrieval narrows it first. Rerank ~20, keep top 3–5.
How do you stop the model from hallucinating in generation?
A grounding prompt: answer only from the numbered passages, no prior knowledge, cite [n] per sentence, refuse with a fixed phrase if unanswerable; plus temperature=0. But prompting only lowers the rate — it can't guarantee faithfulness, which is why verification exists.
temperature=0 and a strict prompt — how can it still be wrong?
temperature=0 removes randomness, not error — if the most-probable output is subtly wrong you get that error deterministically. Prompts bias probabilities, they aren't hard constraints. Failure modes: misreading, paraphrase drift, conflating two chunks, resolving ambiguity wrong. So prevention (prompt) and detection (verification) solve different problems.

Citation verification (the differentiator)

Why verify citations at all if you gave the model the right chunk?
Because a right and a wrong answer look identical to the user, both cited and confident. The model generates (not copies) so it can drift even with the right chunk; and retrieval isn't perfect either. Prompting makes faithfulness likely; verification makes it checked. You can't ship "likely" for facts users act on.
Why must the verifier be independent of the generator?
If it saw the question, other chunks, or the original answer, it would inherit the generator's framing and bias. Seeing only the claim + its cited chunk keeps it an unbiased judge. A citation the generator makes about itself is a self-report, not verification.
What are the ways to verify, and why LLM-as-judge?
String grounding (fast, brittle on paraphrase), NLI/entailment models (calibrated but need torch), and LLM-as-judge (flexible, handles paraphrase, no torch). I used LLM-as-judge because it fits the stack and handles paraphrase; the tradeoff is per-claim API cost and the judge can itself err — mitigated by using a capable/independent model and failing closed.
What do you do when a claim fails verification?
A graduated response: drop/flag the unsupported sentence, keep the supported ones, and escalate to refuse only if most of the answer or the central claim fails — optionally one regeneration attempt first. Refuse is the floor, triggered by a threshold, not by any single failed claim. The exact dial is a product decision driven by how costly a wrong answer is.
How do you handle a hallucinated citation number like [7]?
Bounds-check 0 <= n-1 < len(chunks) before indexing, so an out-of-range citation is skipped (no crash) and the claim ends up unsupported. Uncited sentences are flagged "no citation." Fail-closed throughout.

Evaluation

How do you measure retrieval quality?
Recall@k (is a relevant chunk in the top-k — the ceiling) and MRR (how high is the first relevant hit). nDCG when relevance is graded. I evaluate configs separately (dense/BM25/hybrid/+rerank) to prove each layer earns its place.
How do you measure answer quality?
Faithfulness/groundedness = fraction of claims that pass verification (the verifier doubles as the metric). Citation precision (are made citations correct) and recall (do claims that need citations get correct ones).
How would you build an eval set for production (not hardcoded)?
Bootstrap synthetically — have an LLM generate questions from each chunk (the source chunk is the auto-label) — then grow from real logged traffic, labeled by content or reference-answer (not fragile chunk IDs, which break on re-chunking). Treat the eval set as a living, versioned asset; run it in CI to catch regressions.
Why is a wrong golden label dangerous?
It inverts the metric — correct retrieval scores as a failure — so you chase phantom bugs and "fix" things that were right. The eval set is the ruler; a wrong ruler makes every measurement wrong.

Production & scaling

Where's the latency, and how do you cut it?
Per-item LLM loops dominate: reranking (per candidate) and verification (per claim). Cut it by parallelizing independent calls (bounded thread pool — I got 3.1×), caching deterministic outputs, capping how many candidates/claims, and streaming generation.
How does your embedding cache work and why is it safe?
Key = sha256 of (model + task_type + text), value = the vector, persisted as a pickle. Content-hash keying means changing the model or text auto-misses — it can't serve stale vectors. Cold 5.2s/9 calls → warm 0.0s/0 calls, and it relieves rate limits.
You hit rate limits — how do you handle them properly?
Reactively with exponential backoff (retry only the 429, wait 2→4→8→16s). Proactively with a token-bucket rate limiter that spaces calls under the limit so you never 429. Backoff is the safety net; the limiter is the plan. Caching and parallel-with-a-cap also reduce pressure.
What changes when the corpus is 9 million chunks?
Dense goes from numpy brute-force to ANN (HNSW/IVF) in a vector DB; BM25 to Elasticsearch; full rebuilds to incremental upserts with change-data-capture; script to a FastAPI service that loads the index once and scales horizontally. The architecture is unchanged — only each box's implementation swaps.
What are the security concerns?
Prompt injection via retrieved documents (the corpus is an attack surface — treat retrieved text as untrusted, separate instructions from data), per-tenant access control via metadata filtering so users only retrieve authorized chunks, PII handling, and cost/abuse governance.
What would you improve if you kept going?
Parallelize verification too; wrap the remaining API calls in retry; add a proactive rate limiter; migrate off the deprecated google-generativeai SDK to google-genai; add structured tracing; move embeddings to a real vector DB; and build the synthetic eval-set generator.

Built from scratch as a guided course — chunking, dual indexing, RRF fusion, cross-encoder reranking, grounded generation, independent citation verification, evaluation, and production optimizations (caching + parallelism). The point was to understand every layer, not follow a demo.
