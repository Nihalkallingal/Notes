1. What is NgRx & Why use it

NgRx is a state-management library for Angular, based on the Redux pattern and built on RxJS. It gives your app a single, centralized, immutable store as the one source of truth, and a predictable, one-way way to change that state.

The problem it solves

In a growing app, many unrelated components need the same data. Passing it parent → child → grandchild (and emitting events back up) becomes a tangled mess — "prop drilling" and "state spaghetti." It gets fragile and hard to debug.

🧠 Analogy — the shared Google Sheet: NgRx is like one shared sheet the whole app reads from. Nobody edits a cell directly; instead you submit a request slip (an action), and only specific trusted functions (reducers), following strict rules, actually change the sheet. One source of truth + controlled, traceable changes.

Benefits

  • 🔍 One place to find the app's state.
  • 🧭 Predictable changes — state changes only through a known path.
  • 🐛 Debuggable — every change is a logged action; supports time-travel debugging.
  • 🧪 Testable — reducers & selectors are pure functions.
⚠️ When NOT to use it: NgRx adds boilerplate. For small/simple apps it's overkill — a plain service works fine. It shines in large apps with lots of shared state, complex async flows, and many developers.

3. The Data Flow (the loop)

NgRx is strictly one-directional. Memorize this loop — it's the heart of every interview answer:

Component ──dispatch(action)──▶ Reducer ──returns new state──▶ Store ▲ │ └──────── Selector (component reads via async pipe) ◀──────┘ For async work, an Effect sits in the middle: dispatch(loadUsers) ─▶ Effect listens ─▶ calls Service (HTTP) │ Reducer stores result ◀─ dispatch(loadUsersSuccess) ◀┘
  1. Component dispatches an action.
  2. (If async) an Effect hears it, does the side effect, and dispatches a result action.
  3. The Reducer hears the action and returns a new state object.
  4. The Store updates.
  5. Selectors emit the new value; the component's async pipe re-renders.

4. Walkthrough 1 — The Counter (synchronous)

No side effects · pure state change

State (counter.state.ts)

export interface CounterState {
  count: number;
}

export const initialCounterState: CounterState = {
  count: 0
};

Actions (counter.actions.ts)

import { createAction } from '@ngrx/store';

export const increment = createAction('[Counter] Increment');
export const decrement = createAction('[Counter] Decrement');
export const reset     = createAction('[Counter] Reset');

Naming convention: '[Source] Event' — readable in DevTools logs. These carry no payload.

Reducer (counter.reducer.ts)

import { createReducer, on } from '@ngrx/store';
import { increment, decrement, reset } from './counter.actions';
import { CounterState, initialCounterState } from './counter.state';

export const counterReducer = createReducer(
  initialCounterState,
  on(increment, (state) => ({ ...state, count: state.count + 1 })),
  on(decrement, (state) => ({ ...state, count: state.count - 1 })),
  on(reset,     (state) => ({ ...state, count: 0 }))
);
✅ Golden rule — immutability: A reducer never mutates the existing state. It returns a brand-new object (the ...state spread = "photocopy with one change"). This is what enables time-travel & change detection.

Selectors (counter.selectors.ts)

import { createFeatureSelector, createSelector } from '@ngrx/store';
import { CounterState } from './counter.state';

export const selectCounter = createFeatureSelector<CounterState>('counter');

export const selectCount = createSelector(
  selectCounter,
  (state) => state.count
);

// Derived selectors — compute, don't store:
export const selectIsEven = createSelector(selectCount, (c) => c % 2 === 0);
export const selectDoubleCount = createSelector(selectCount, (c) => c * 2);

Register in the module

StoreModule.forRoot({ counter: counterReducer })

Component

export class AppComponent {
  count$: Observable<number> = this.store.select(selectCount);

  constructor(private store: Store) {}

  onIncrement() { this.store.dispatch(increment()); }
  onDecrement() { this.store.dispatch(decrement()); }
  onReset()     { this.store.dispatch(reset()); }
}

Template

<h2>Count: {{ count$ | async }}</h2>
<button (click)="onIncrement()">+</button>
<button (click)="onDecrement()">-</button>
<button (click)="onReset()">Reset</button>

The async pipe auto-subscribes to the observable and auto-unsubscribes on destroy (prevents memory leaks).

5. Walkthrough 2 — Users list (async + Effects)

HTTP call · the real reason Effects exist

Model (user.model.ts)

export interface User {
  id: number;
  name: string;
  email: string;
}

State — the { data, loading, error } trio (user.state.ts)

export interface UserState {
  users: User[];
  loading: boolean;
  error: string | null;
}

export const initialUserState: UserState = {
  users: [],
  loading: false,
  error: null
};

Actions — the async trio (user.actions.ts)

import { createAction, props } from '@ngrx/store';
import { User } from './user.model';

export const loadUsers = createAction('[User] Load Users');
export const loadUsersSuccess = createAction(
  '[User] Load Users Success',
  props<{ users: User[] }>()     // carries a payload
);
export const loadUsersFailure = createAction(
  '[User] Load Users Failure',
  props<{ error: string }>()
);
💡 props<T>() defines the payload (the data an action carries). The Trigger → Success → Failure trio is the universal recipe for ANY async operation.

Service — the only place that knows the URL (user.service.ts)

@Injectable({ providedIn: 'root' })
export class UserService {
  private apiUrl = 'https://jsonplaceholder.typicode.com/users';
  constructor(private http: HttpClient) {}

  getUsers(): Observable<User[]> {
    return this.http.get<User[]>(this.apiUrl);
  }
}

Single responsibility: the service knows nothing about NgRx; it just fetches data.

Effect — the bridge (user.effects.ts)

@Injectable()
export class UserEffects {
  loadUsers$ = createEffect(() =>
    this.actions$.pipe(
      ofType(loadUsers),                                  // 1. LISTEN
      switchMap(() =>                                     // 2. DO async work
        this.userService.getUsers().pipe(
          map((users) => loadUsersSuccess({ users })),    // 3a. SUCCESS → new action
          catchError((error) =>
            of(loadUsersFailure({ error: error.message }))) // 3b. FAILURE → new action
        )
      )
    )
  );

  constructor(
    private actions$: Actions,
    private userService: UserService
  ) {}
}
PieceMeaning
actions$A stream of every action dispatched in the app.
ofType(loadUsers)Filter — only react to this action.
switchMapRun the async call; cancels a previous in-flight call if a new one starts (good for loads).
mapTransform the result into a success action.
catchError + of(...)On failure, emit a failure action. of() wraps a value into an Observable (everything in the pipe must be a stream).
✅ Effect rule: an effect listens for one action and (by default) returns a new action. Listen → do → dispatch.

Reducer — reads payload via destructuring (user.reducer.ts)

export const userReducer = createReducer(
  initialUserState,
  on(loadUsers,        (state) => ({ ...state, loading: true, error: null })),
  on(loadUsersSuccess, (state, { users }) => ({ ...state, loading: false, users })),
  on(loadUsersFailure, (state, { error }) => ({ ...state, loading: false, error }))
);

(state, { users }) destructures the payload defined by props().

Selectors (user.selectors.ts)

export const selectUserState = createFeatureSelector<UserState>('users');
export const selectAllUsers     = createSelector(selectUserState, (s) => s.users);
export const selectUsersLoading = createSelector(selectUserState, (s) => s.loading);
export const selectUsersError   = createSelector(selectUserState, (s) => s.error);

Register everything (app.module.ts)

imports: [
  HttpClientModule,                                  // enables HttpClient
  StoreModule.forRoot({ counter: counterReducer, users: userReducer }),
  EffectsModule.forRoot([UserEffects]),              // registers effects
  StoreDevtoolsModule.instrument({ maxAge: 25, logOnly: false })
]

StoreModule.forRoot({...}) takes an object (slice → reducer). EffectsModule.forRoot([...]) takes an array of effect classes.

Component — kick off load in ngOnInit

export class AppComponent implements OnInit {
  users$   = this.store.select(selectAllUsers);
  loading$ = this.store.select(selectUsersLoading);
  error$   = this.store.select(selectUsersError);

  constructor(private store: Store) {}

  ngOnInit() { this.store.dispatch(loadUsers()); }
}

Template — three-state UI

<p *ngIf="loading$ | async">Loading...</p>
<p *ngIf="error$ | async as error">Error: {{ error }}</p>
<ul>
  <li *ngFor="let user of users$ | async">
    {{ user.name }} — {{ user.email }}
  </li>
</ul>
On page load: 1. ngOnInit dispatches loadUsers 2. Reducer sets loading:true → spinner shows 3. Effect hears loadUsers → calls service → HTTP request 4. Response → effect dispatches loadUsersSuccess({ users }) 5. Reducer stores users, loading:false 6. selectAllUsers emits → list renders

6. @ngrx/entity — Normalized Collections (all methods)

Managing lists of records with less code

The problem & the idea

Storing a collection as a plain User[] array forces you to hand-write add/update/remove/find logic in every reducer, and lookups by id are slow (O(n) — loop the array). @ngrx/entity stores collections normalized for fast (O(1)) id lookups and gives you ready-made immutable CRUD methods + selectors.

// Normalized shape entity manages for you:
{
  ids: [1, 2, 3],                    // order
  entities: {                        // dictionary keyed by id (instant lookup)
    1: { id: 1, name: 'Leanne', ... },
    2: { id: 2, name: 'Ervin',  ... },
    3: { id: 3, name: 'Clementine', ... }
  }
}
🧠 Analogy: an array is a guest list you read top-to-bottom; the normalized shape is a wall of numbered lockers — "give me #5" is instant.

Setup

import { EntityState, EntityAdapter, createEntityAdapter } from '@ngrx/entity';
import { User } from './user.model';

// 1. Slice extends EntityState<User> → inherits ids + entities
export interface UserState extends EntityState<User> {
  loading: boolean;
  error: string | null;
}

// 2. Create the adapter (the toolbox). Optionally customize:
export const userAdapter: EntityAdapter<User> = createEntityAdapter<User>({
  // selectId: (u) => u.id,                 // default is `id`; override if your key differs
  // sortComparer: (a, b) => a.name.localeCompare(b.name)  // keep ids sorted, or false
});

// 3. Initial state = empty collection + your extra fields
export const initialUserState: UserState = userAdapter.getInitialState({
  loading: false,
  error: null
});

📋 All EntityAdapter methods

Every method takes the data + current state and returns a new immutable state (use inside reducer on() handlers).

MethodWhat it does
addOne(entity, state)Add one entity (ignored if its id already exists).
addMany(entities, state)Add multiple entities.
setOne(entity, state)Add or replace one entity by id.
setMany(entities, state)Add or replace many.
setAll(entities, state)Replace the entire collection (perfect for load-success).
removeOne(id, state)Remove one entity by id.
removeMany(ids, state)Remove many by ids — or pass a predicate (entity) => boolean.
removeAll(state)Clear the whole collection.
updateOne({ id, changes }, state)Shallow-merge changes into the entity with that id.
updateMany(updates, state)Apply many { id, changes } updates.
upsertOne(entity, state)Update if exists, else add.
upsertMany(entities, state)Upsert many.
mapOne({ id, map }, state)Apply a map function to one entity (NgRx 8+).
map(mapFn, state)Apply a map function to all entities (e.g. mark all read).
getInitialState(extras?)Build { ids: [], entities: {} } + your extra fields.
getSelectors(selectState?)Returns selectAll, selectEntities, selectIds, selectTotal.

Example usage in a reducer

on(loadUsersSuccess,  (state, { users }) => userAdapter.setAll(users, { ...state, loading: false })),
on(addUser,           (state, { user })  => userAdapter.addOne(user, state)),
on(updateUserSuccess, (state, { id, changes }) => userAdapter.updateOne({ id, changes }, state)),
on(deleteUserSuccess, (state, { id })   => userAdapter.removeOne(id, state)),
on(clearUsers,        (state)           => userAdapter.removeAll(state));

The 4 built-in selectors (getSelectors())

SelectorReturnsUse for
selectAllUser[] (array)Rendering a list (*ngFor)
selectEntities{ [id]: User } (dictionary)Instant lookup by id (detail page)
selectIdsnumber[]Existence checks, ordering, keys only
selectTotalnumberShowing a count
const { selectAll, selectEntities, selectIds, selectTotal } = userAdapter.getSelectors();

export const selectUserState = createFeatureSelector<UserState>('users');
export const selectAllUsers  = createSelector(selectUserState, selectAll);   // → User[]
export const selectUserCount = createSelector(selectUserState, selectTotal); // → number
✅ Win: selectAllUsers still returns a User[], so components/templates need no changes — normalization is hidden behind the selector.

7. Walkthrough 3 — Delete a user (Effect + removeOne)

Full async write operation, end-to-end

Actions (add to user.actions.ts)

export const deleteUser = createAction('[User] Delete User', props<{ id: number }>());
export const deleteUserSuccess = createAction('[User] Delete User Success', props<{ id: number }>());
export const deleteUserFailure = createAction('[User] Delete User Failure', props<{ error: string }>());

Trigger & success carry the id so the reducer knows which entity to remove.

Service (add to user.service.ts)

deleteUser(id: number): Observable<void> {
  return this.http.delete<void>(`${this.apiUrl}/${id}`);
}

Effect (add to user.effects.ts)

deleteUser$ = createEffect(() =>
  this.actions$.pipe(
    ofType(deleteUser),
    mergeMap(({ id }) =>                                  // mergeMap: don't cancel concurrent deletes
      this.userService.deleteUser(id).pipe(
        map(() => deleteUserSuccess({ id })),             // forward the id (DELETE returns void)
        catchError((error) => of(deleteUserFailure({ error: error.message })))
      )
    )
  )
);
⚠️ switchMap vs mergeMap (a classic interview question):
  • switchMap — cancels the previous inner observable when a new action arrives. Use for reads/searches/loads (only the latest matters).
  • mergeMap — runs all inner observables in parallel; cancels nothing. Use for independent writes like delete/create (every one must complete).
  • concatMap — queues them to run one-after-another, in order. Use for ordered writes.
  • exhaustMap — ignores new actions while one is in flight. Use to prevent double-submit (e.g. login button).

Reducer (add to user.reducer.ts)

on(deleteUserSuccess, (state, { id }) => userAdapter.removeOne(id, state)),
on(deleteUserFailure, (state, { error }) => ({ ...state, error }))
⚠️ Most common beginner bug: forgetting the comma between on() handlers inside createReducer. Each handler is a comma-separated argument.

Component + template

// component
onDeleteUser(id: number) { this.store.dispatch(deleteUser({ id })); }
<li *ngFor="let user of users$ | async">
  {{ user.name }} — {{ user.email }}
  <button (click)="onDeleteUser(user.id)">🗑️ Delete</button>
</li>
On 🗑️ click: 1. onDeleteUser(id) dispatches deleteUser({ id }) 2. Effect hears it → service HTTP DELETE 3. Success → dispatch deleteUserSuccess({ id }) 4. Reducer → userAdapter.removeOne(id, state) 5. selectAllUsers emits smaller array → row disappears

8. Parameterized Selectors (selectUserById)

Sometimes you need to select one item by an argument (e.g. a route param). Pattern: a function that returns a selector ("selector factory"). Combine with selectEntities for instant O(1) lookup.

export const selectUserEntities = createSelector(selectUserState, selectEntities);

// A function that takes an id and returns a selector for that one user:
export const selectUserById = (id: number) =>
  createSelector(selectUserEntities, (entities) => entities[id]);

// Usage in a component:
this.user$ = this.store.select(selectUserById(3));   // → the User with id 3 (or undefined)
💡 Interview point: the (param) => createSelector(...) shape is how selectors take arguments. Using selectEntities[id] is why entity normalization gives fast lookups.

9. @ngrx/router-store + Walkthrough 4 (/users/:id)

Routing state becomes part of the store

Why

The URL is state too: which page (/users), which record (/users/5 — a route param), which filters (?sort=name — query params). Normally this lives in the Angular Router (ActivatedRoute), separate from the store — two sources of truth. @ngrx/router-store connects the Router to the store so routing is just another slice: readable via selectors and observable in effects.

🧠 Analogy: it copies the browser's address bar into the shared Google Sheet, so "which page / which id / which filters" sits alongside all other state — one source of truth.

What it does on every navigation

  • Stores a serialized snapshot of router state in a router slice (url, params, queryParams).
  • Dispatches navigation actions: ROUTER_REQUEST → ROUTER_NAVIGATION → ROUTER_NAVIGATED (and ROUTER_CANCEL / ROUTER_ERROR) — listenable in effects.

Setup (app.module.ts)

import { StoreRouterConnectingModule, routerReducer } from '@ngrx/router-store';

imports: [
  StoreModule.forRoot({ counter: counterReducer, users: userReducer, router: routerReducer }),
  StoreRouterConnectingModule.forRoot(),   // bridges Router ↔ Store
  // (optional) StoreRouterConnectingModule.forRoot({ serializer: MinimalRouterStateSerializer })
]

Router selectors (router.selectors.ts)

import { getRouterSelectors } from '@ngrx/router-store';

export const {
  selectCurrentRoute, selectUrl,
  selectRouteParams, selectRouteParam,   // selectRouteParam('id') → the :id value (a string)
  selectQueryParams, selectQueryParam
} = getRouterSelectors();

Combine URL + entity for the selected record

// "read the :id from the URL, then look it up in the entities dictionary"
export const selectSelectedUser = createSelector(
  selectRouteParam('id'),
  selectUserEntities,
  (id, entities) => (id ? entities[Number(id)] : undefined)   // param is a string → Number()
);

Detail component — no ActivatedRoute needed

@Component({ selector: 'app-user-detail', template: `...{{ (user$ | async)?.name }}...` })
export class UserDetailComponent {
  user$ = this.store.select(selectSelectedUser);   // derived purely from the URL via the store
  constructor(private store: Store) {}
}

Route + links

// app-routing.module.ts
const routes: Routes = [{ path: 'users/:id', component: UserDetailComponent }];

// template
<a [routerLink]="['/users', user.id]">{{ user.name }}</a>
<router-outlet></router-outlet>
Click a user: 1. routerLink → URL becomes /users/5 2. router-store dispatches ROUTER_NAVIGATED, updates router slice → { id: '5' } 3. UserDetailComponent renders in the outlet 4. selectSelectedUser reads id from router slice + entities[5] → emits the user 5. Detail page shows — driven entirely by the URL, zero ActivatedRoute
⚠️ Gotcha: opening /users/5 on a fresh reload may show "not found" because the list hasn't been fetched yet. Real apps dispatch loadUsers/loadUser on that route (e.g. via a navigation effect or resolver).

10. Key Patterns to Remember

  • The async trio: load → loadSuccess → loadFailure. Reuse for every async op (load/save/delete).
  • The state trio: { data, loading, error } for any server data, so the UI can show spinner / data / error.
  • Immutability: always return a new object with ...spread; never mutate state.
  • Reducers are pure: no HTTP, no Date.now(), no side effects. Side effects go in Effects.
  • Don't store what you can derive: compute via selectors (memoized) instead of storing redundant fields.
  • Feature-selector first: grab the slice once, then compose smaller selectors on top.
  • Service ≠ NgRx: keep HTTP logic in a service; the effect just calls it.
  • async pipe over manual .subscribe() in templates (auto-unsubscribe).

11. Redux DevTools & Traceability

Install the Redux DevTools browser extension + the @ngrx/store-devtools package, then add StoreDevtoolsModule.instrument(...). Open DevTools → Redux tab.

  • Action log — every action in order (the full story of what happened).
  • Action / State / Diff tabs — see the action, the full state at that moment, and exactly what changed.
  • Time-travel — drag the slider to replay state changes; the UI rewinds.
  • maxAge — how many actions to keep; logOnly false in dev for full powers, true in prod.
💡 Interview gold: this is the concrete payoff of "every change is a named, traceable action" — impossible with a raw BehaviorSubject.

12. NgRx vs a Shared Service + BehaviorSubject

A common, valid question: "Why not just a service with a BehaviorSubject?" For small apps — you can! The difference is about control and scale.

Key insight: with a BehaviorSubject, any component can call .next(anything) and directly overwrite state with any value. With NgRx, a component can only dispatch a predefined action (request a change); the reducer alone decides how state actually changes.

Service + BehaviorSubjectNgRx
Who can changeAnyone (open)Anyone can request (open)
HOW it changesOpen — set to any value, anywhereLocked — only via finite, named actions + one reducer
Possible changesInfinite / undocumentedFinite / documented (your actions file)
Change historyNoneFull action log + time-travel
BoilerplateMinimalMore
Best forSmall / simple appsLarge apps, complex async, many devs
🏦 Analogy: BehaviorSubject = an open vault anyone can take from. NgRx = a bank where you submit a request slip and only the teller (reducer), following fixed rules, touches the money — and every request is logged.

15. Interview Questions & Answers

Q1. What is NgRx and what problem does it solve?
A state-management library for Angular implementing the Redux pattern on RxJS. It centralizes shared state into one immutable store with a predictable, one-way data flow, solving prop-drilling and unpredictable state in large apps.
Q2. Explain the data flow.
Component dispatches an action → (effects handle any async, dispatching a result action) → reducer produces a new state → store updates → selectors emit → component re-renders via the async pipe. Strictly one-directional.
Q3. What is an action? Does it change state?
A plain object with a type (and optional payload) describing that something happened. It does NOT change state itself — it just announces an event; the reducer decides the change.
Q4. Why must reducers be pure / immutable?
Purity (same input → same output, no side effects) + immutability (return new objects) enable predictable state, efficient change detection, and time-travel debugging. Mutating would break all three.
Q5. What are Effects and why do we need them?
Reducers can't do async/side effects. Effects are the designated place for them: they listen for an action, perform the side effect (e.g. HTTP), then dispatch a success/failure action. Keeps reducers pure.
Q6. What are selectors and why use them?
Pure, memoized functions to read or derive state. They decouple components from the store's shape, are reusable/composable, and only recompute when inputs change (performance).
Q7. switchMap vs mergeMap vs concatMap vs exhaustMap in effects?
switchMap cancels the previous inner call (good for searches/loads). mergeMap runs all in parallel (independent ops). concatMap queues them in order (ordered saves). exhaustMap ignores new ones while one is running (login button spam).
Q8. props() — what is it?
It declares the typed payload an action carries, e.g. createAction('[User] Load Success', props<{ users: User[] }>()).
Q9. forRoot vs forFeature?
forRoot registers root/global state and effects once at the app level; forFeature registers state/effects scoped to a (often lazy-loaded) feature module.
Q10. How do you handle loading and error states?
Model the slice as { data, loading, error }. On the trigger action set loading:true; on success store data & loading:false; on failure store the error. The template shows spinner / data / error accordingly.
Q11. NgRx vs a service with BehaviorSubject — when to choose which?
Service+Subject is fine for small/simple shared state. Choose NgRx for large apps needing predictable, traceable, centralized state with complex async — it constrains how state changes (named actions + one reducer) and gives an audit log + DevTools.
Q12. What does @ngrx/entity do?
Provides an adapter to manage collections in a normalized { ids, entities } shape, with ready-made CRUD methods (addOne, updateOne, setAll…) and selectors (selectAll, etc.) — avoids hand-writing array logic.
Q13. What is a meta-reducer?
A higher-order reducer that wraps your reducers and runs on every action — used for cross-cutting concerns like logging or persisting state to localStorage (rehydrate on startup).
Q14. Why the async pipe instead of subscribing manually?
It auto-subscribes and, crucially, auto-unsubscribes when the component is destroyed — preventing memory leaks and reducing boilerplate.
Q15. Action naming convention?
'[Source] Event', e.g. '[User] Load Users Success' — makes the DevTools action log readable and groups actions by feature.
Q16. How does @ngrx/entity store a collection, and why?
Normalized as { ids: [...], entities: { [id]: item } }. The dictionary gives O(1) lookup by id (vs O(n) array search) and avoids duplicates, while ids preserves order. The adapter provides immutable CRUD methods and selectors so you don't hand-write array logic.
Q17. Name the main EntityAdapter methods.
CRUD: addOne/addMany, setOne/setMany/setAll, upsertOne/upsertMany, updateOne/updateMany, removeOne/removeMany/removeAll, mapOne/map. Plus getInitialState() and getSelectors() (→ selectAll, selectEntities, selectIds, selectTotal). setAll for load-success; removeOne for delete; updateOne({id, changes}) for edits.
Q18. How do you create a selector that takes an argument (e.g. by id)?
Use a selector factory — a function that returns a selector: export const selectUserById = (id) => createSelector(selectUserEntities, (entities) => entities[id]); then store.select(selectUserById(3)). Pairs perfectly with entity's selectEntities for instant lookup.
Q19. For a delete (write) effect, which flattening operator and why?
mergeMap (or concatMap if order matters) — independent writes must all complete. switchMap would be wrong because deleting a second item could cancel the first delete's request. switchMap is for reads/searches where only the latest result matters.
Q20. What's the most common reducer syntax mistake?
Forgetting the comma between on() handlers inside createReducer(initialState, on(...), on(...)) — each handler is a comma-separated argument.
Q21. What is @ngrx/router-store and why use it?
It connects the Angular Router to the store: on each navigation it stores a serialized router snapshot in a router slice and dispatches navigation actions (ROUTER_NAVIGATED, etc.). This makes routing a single source of truth — you can select route/query params via selectors and react to navigation in effects, with full DevTools traceability. Register with routerReducer + StoreRouterConnectingModule.forRoot().
Q22. How do you read a route param (e.g. :id) without injecting ActivatedRoute?
Use getRouterSelectors() from router-store to get selectRouteParam, then compose: createSelector(selectRouteParam('id'), selectUserEntities, (id, entities) => entities[Number(id)]). The param is a string, so convert with Number(). The component just selects this — no ActivatedRoute.
Q23. A route param change should load data — where does that logic go?
In an effect listening for routerNavigatedAction (or ROUTER_NAVIGATED): inspect the url/params and dispatch the load action (e.g. loadUser({ id })). Alternatively use a route resolver. Keeps components dumb and data-loading reactive to navigation.
